Triage checklist

How an L2/L3 engineer works a problem, in order:

1 · Metrics — what is abnormal?

  • Which service deviated first? (blast radius starts there)
  • Is it saturation (CPU/mem), latency, or errors?
  • Did dependents degrade after? (points upstream)

2 · Logs — what was it doing?

  • Errors/exceptions around the problem start time
  • OOMKilled / exit 137 → memory; CrashLoopBackOff → startup or limits
  • Correlate with deploys and config changes

3 · Traces — where is time spent?

  • Slowest spans: DB query, downstream call, or in-process?
  • One slow dependency poisons every caller — fix the root, not the callers

4 · Infra — what changed underneath?

  • Node pressure, noisy neighbors, AZ network events
  • Connection pool exhaustion vs. genuinely slow queries

Per-scenario hints

  • CPU saturation: thread dumps → hot method; scale out or kill the runaway thread.
  • Memory leak: heap trend climbing between restarts = leak, not load. Exit 137 confirms OOM kill.
  • DB slowdown: check top SQL / execution plans; one missing index slows the whole chain.
  • Crash loop: previous container logs (not current) hold the crash reason.
  • Latency spike: affects all callers equally — suspect the network path, not the code.
