Easy

1. Pod vs Deployment vs Service — one line each.

Answer: Pod runs the containers; Deployment manages replicas and rollouts; Service gives stable networking to the pods.

2. First two commands for a CrashLooping pod?

Answer: kubectl describe pod/<name> and kubectl logs <name> --previous.

Medium

3. Worked yesterday, CrashLoops today right after a release. Action?

Answer: kubectl rollout history deployment/<name>, then kubectl rollout undo — bad image until proven otherwise.

4. Ingress returns 404 for one path but 503 for another. Meaning?

Answer: 404 = no ingress rule matched the path; 503 = a rule matched but there are no healthy endpoints (often a port-name mismatch).

Hard

5. Deploy fails with 'Forbidden: exceeded quota'. Diagnose?

Answer: ResourceQuota or LimitRange in the namespace — kubectl describe quota; then request a quota increase or trim the requests.

6. A node keeps evicting pods with DiskPressure. Beyond deleting evicted pods?

Answer: Find what fills the disk (logs, emptyDir) and fix the source, or the evictions repeat within the hour — use cordon/drain discipline for node work.

Kubernetes for Production Support

The kubectl commands and mental models for triaging Kubernetes incidents: what is unhealthy, why a pod will not start, and how to read the story the cluster is telling.

Learning path DevOps & CI/CD Track 2 of 7

Key takeaways

  • Pod < Deployment < Service: know which of the three layers you're debugging before you run commands.
  • kubectl describe + kubectl logs (--previous) is the triage pair that solves most incidents.
  • CrashLoop right after a release = bad image until proven otherwise — rollout undo is the fastest fix.
  • ImagePullBackOff and Pending are scheduler/registry problems, not application bugs.
  • Probes, HPA, PDBs and helm status are the guardrails — diff staging vs prod values before diffing code.

Pods, Deployments, Services: the three layers

A Pod is the smallest unit — one or more containers that live and die together. You almost never manage pods directly: a Deployment owns a set of identical pods (a ReplicaSet) and keeps the desired count running. A Service is the stable network endpoint in front of those pods, because pod IPs change on every restart. When support hears "the app is down", the check order is: Service → Deployment → Pods → container logs. Skipping straight to logs wastes the first ten minutes.

kubectl get pods -n trading # pod states: Running? CrashLoopBackOff? Pending? kubectl get deployments -n trading # desired vs available replicas kubectl get services -n trading # cluster IPs and ports kubectl top pods -n trading # live CPU/memory per pod

The triage pair: describe and logs

kubectl describe pod shows the pod's recent history — restarts, the last termination reason, and the Events section at the bottom, which is the cluster's own incident log. kubectl logs shows what the application said:

kubectl describe pod trade-api-7d9f8c6b5-x2k4p -n trading kubectl logs trade-api-7d9f8c6b5-x2k4p -n trading --tail=100 kubectl logs trade-api-7d9f8c6b5-x2k4p -n trading --previous # logs of the LAST, crashed instance

The --previous flag is the one people forget: without it you read the fresh container's logs, which say nothing, while the crash evidence died with the previous instance.

CrashLoopBackOff: reading the loop

CrashLoopBackOff means the container starts, dies, and Kubernetes retries with increasing backoff. The diagnosis is in the previous logs plus the last termination state in describe output:

  • Exit 137 / OOMKilled — memory limit too low or a leak. Check kubectl top and the memory request/limit in the deployment.
  • Exit 1 with a stack trace — application bug or bad config. Look for missing env vars or unreachable dependencies in the first log lines.
  • Liveness probe failures — the app starts but the probe kills it. Often the probe path is wrong or the startup takes longer than the initial delay.

What support watches. A deployment that worked yesterday and CrashLoops today after a release is a bad image until proven otherwise. kubectl rollout history deployment/trade-api -n trading shows revisions; kubectl rollout undo rolls back. Knowing the rollback command before the incident is the difference between a 5-minute and a 50-minute outage.

ImagePullBackOff and Pending: the other two states

ImagePullBackOff — the node cannot fetch the image. Causes in order of likelihood: typo in the image tag, missing imagePullSecret for a private registry, or the registry itself being down. kubectl describe pod names the exact failure.

Pending — the pod was never scheduled. Usually insufficient CPU/memory on the nodes, or a PersistentVolumeClaim that cannot be satisfied. kubectl describe pod events say plainly: "0/3 nodes are available: 3 Insufficient memory."

Probes and HPA: the guardrails

Liveness probes decide whether to restart a stuck container; readiness probes decide whether it receives traffic. A readiness probe failing across all pods means the Service has no endpoints — the app looks "up" in pod listings while serving nothing. Check with kubectl get endpoints.

The HorizontalPodAutoscaler scales replicas on CPU or custom metrics. During a traffic spike, verify the HPA is actually scaling (kubectl get hpa) and that the deployment's max replicas and the nodes' capacity can absorb the load — autoscaling into an unschedulable state just creates Pending pods faster.

Incident walkthrough: pricing service down

Alert: pricing API returning 503s. The sequence:

  • kubectl get pods -n pricing — 2 of 4 pods in CrashLoopBackOff, restarts climbing.
  • kubectl logs --previous on a crashed pod — OutOfMemoryError in the first 40 lines, exit 137 in describe.
  • kubectl top pods — surviving pods near their memory limit too: a leak, not a one-off.
  • Check the deployment: memory limit unchanged for months, but today's release doubled the cache size (from the rollout history).
  • Mitigate: kubectl rollout undo to the previous revision; service recovers. Root cause goes to development with the OOM evidence attached.

Total time with this sequence: minutes. The pattern is always the same — states, previous logs, describe events, recent changes — and it works for nearly every Kubernetes incident.

Helm: releases, history and rollback

Most bank workloads deploy via Helm charts, not raw YAML. A Helm release is a versioned deployment of a chart; every upgrade increments the revision and keeps the history:

helm list -n trading # releases and their status helm history trade-api -n trading # every revision with timestamps helm rollback trade-api 4 -n trading # back to revision 4

Rollback swaps the live manifests back — faster and safer than editing values by hand during an incident. The stuck state to know: a failed upgrade leaves the release pending-upgrade, which blocks every later operation. helm rollback clears it; if rollback itself fails, check for a half-applied resource with kubectl get before forcing anything.

What support watches. helm status shows the exact values the release was installed with — when "it worked in staging" but fails in prod, diff the two releases' values before diffing the code.

Quotas and limits: "Forbidden: exceeded quota"

A deployment that fails instantly with Forbidden: exceeded quota is not an application problem — the namespace hit its ResourceQuota (max pods, CPU, memory for the whole namespace) or a LimitRange rejected the pod's resource requests:

kubectl describe resourcequota -n trading # used vs hard limits kubectl describe limitrange -n trading # default/min/max per pod kubectl get events -n trading --sort-by=.lastTimestamp | tail -20

Classic scenario: the quota allows 50 pods, the HPA just scaled to 51 during a traffic spike, and the 51st pod is rejected. The events stream says so plainly. Support's escalation is precise: "namespace trading is at 50/50 pods against quota; request a quota increase or scale something down" — not "Kubernetes is broken."

Ingress debugging: 404 vs 503

The ingress is the front door; its errors have distinct meanings:

  • 404 from the ingress — no rule matched the host or path. Check kubectl describe ingress -n trading: the host spelling, the path prefix, and whether the rule points at the right Service name and port.
  • 503 from the ingress — the rule matched but the Service has no healthy backends. Check kubectl get endpoints: empty endpoints mean every pod is failing its readiness probe (the app is "running" but not serving).
  • Port name mismatch — the Service targets port: http but the Deployment exposes containerPort: 8080 under a different name. Traffic goes nowhere and the error looks like an app failure.

Debug order: ingress rules → service → endpoints → pod readiness. Each layer has exactly one command, and skipping layers is how 404s get "fixed" by restarting pods that were never the problem.

Node pressure and evictions

When a node runs out of disk or memory, the kubelet starts evicting pods to protect the node. kubectl describe node shows the Conditions section:

kubectl describe node node-3 | grep -A 3 Conditions kubectl get pods -n trading | grep Evicted kubectl top node

DiskPressure: True is usually runaway container logs or an emptyDir filling up; MemoryPressure: True means the node's RAM is exhausted and BestEffort pods die first. Evicted pods are a node capacity problem — rescheduling the workload does not help if every node is full. The operational discipline: kubectl cordon a sick node so nothing new lands on it, kubectl drain to move workloads off gracefully, then fix the underlying disk or memory shortage.

Key takeaway. An Evicted pod is the cluster protecting itself. Do not just delete evicted pods and move on — find what filled the disk or memory, or the evictions repeat within the hour.

Production readiness checklist

Before any workload enters the prod cluster, it passes this gate. Every item is a past incident:

CheckWhy it exists
requests = limits (or justified gap)Unbounded containers get OOMKilled at 3am; requests drive scheduling
Liveness + readiness probesWithout readiness, a starting pod takes traffic and fails it
PodDisruptionBudgetNode upgrades evict everything at once without one
NetworkPoliciesDefault-allow once let a compromised pod scan the cluster
ResourceQuota + LimitRangeOne namespace's runaway job starved the whole cluster
Pod anti-affinityAll three replicas landed on the same node; the node died
Image pull secret + pinned digest:latest moved under a running deployment
Log + metric scrapingIf it is not in the dashboards, it does not exist during an incident

A failed readiness review

What happened. The pricing-engine deploy passed CI and went to prod Friday evening. Saturday 02:14: no liveness probe, so when the JVM wedged on a full GC, kubelet kept it in service - it accepted requests and timed every one out for 40 minutes before anyone noticed. No PDB either, so the Sunday node patch evicted its only two replicas simultaneously.

The outcome. Rollback, then the checklist became a merge gate: no probes, no PDB, no deploy. Three incidents that quarter traced to the same missing six lines of YAML.

Support takeaway: most Kubernetes incidents are not Kubernetes problems - they are missing guardrails. When triaging, check the guardrails first: kubectl get pdb,networkpolicy -A plus the deployment's probe definitions tell you in seconds whether this workload was ever prod-ready.
