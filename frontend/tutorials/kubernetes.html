Kubernetes for Production Support

The kubectl commands and mental models for triaging Kubernetes incidents: what is unhealthy, why a pod will not start, and how to read the story the cluster is telling.

Pods, Deployments, Services: the three layers

A Pod is the smallest unit — one or more containers that live and die together. You almost never manage pods directly: a Deployment owns a set of identical pods (a ReplicaSet) and keeps the desired count running. A Service is the stable network endpoint in front of those pods, because pod IPs change on every restart. When support hears "the app is down", the check order is: Service → Deployment → Pods → container logs. Skipping straight to logs wastes the first ten minutes.

kubectl get pods -n trading # pod states: Running? CrashLoopBackOff? Pending? kubectl get deployments -n trading # desired vs available replicas kubectl get services -n trading # cluster IPs and ports kubectl top pods -n trading # live CPU/memory per pod

The triage pair: describe and logs

kubectl describe pod shows the pod's recent history — restarts, the last termination reason, and the Events section at the bottom, which is the cluster's own incident log. kubectl logs shows what the application said:

kubectl describe pod trade-api-7d9f8c6b5-x2k4p -n trading kubectl logs trade-api-7d9f8c6b5-x2k4p -n trading --tail=100 kubectl logs trade-api-7d9f8c6b5-x2k4p -n trading --previous # logs of the LAST, crashed instance

The --previous flag is the one people forget: without it you read the fresh container's logs, which say nothing, while the crash evidence died with the previous instance.

CrashLoopBackOff: reading the loop

CrashLoopBackOff means the container starts, dies, and Kubernetes retries with increasing backoff. The diagnosis is in the previous logs plus the last termination state in describe output:

  • Exit 137 / OOMKilled — memory limit too low or a leak. Check kubectl top and the memory request/limit in the deployment.
  • Exit 1 with a stack trace — application bug or bad config. Look for missing env vars or unreachable dependencies in the first log lines.
  • Liveness probe failures — the app starts but the probe kills it. Often the probe path is wrong or the startup takes longer than the initial delay.

What support watches. A deployment that worked yesterday and CrashLoops today after a release is a bad image until proven otherwise. kubectl rollout history deployment/trade-api -n trading shows revisions; kubectl rollout undo rolls back. Knowing the rollback command before the incident is the difference between a 5-minute and a 50-minute outage.

ImagePullBackOff and Pending: the other two states

ImagePullBackOff — the node cannot fetch the image. Causes in order of likelihood: typo in the image tag, missing imagePullSecret for a private registry, or the registry itself being down. kubectl describe pod names the exact failure.

Pending — the pod was never scheduled. Usually insufficient CPU/memory on the nodes, or a PersistentVolumeClaim that cannot be satisfied. kubectl describe pod events say plainly: "0/3 nodes are available: 3 Insufficient memory."

Probes and HPA: the guardrails

Liveness probes decide whether to restart a stuck container; readiness probes decide whether it receives traffic. A readiness probe failing across all pods means the Service has no endpoints — the app looks "up" in pod listings while serving nothing. Check with kubectl get endpoints.

The HorizontalPodAutoscaler scales replicas on CPU or custom metrics. During a traffic spike, verify the HPA is actually scaling (kubectl get hpa) and that the deployment's max replicas and the nodes' capacity can absorb the load — autoscaling into an unschedulable state just creates Pending pods faster.

Incident walkthrough: pricing service down

Alert: pricing API returning 503s. The sequence:

  • kubectl get pods -n pricing — 2 of 4 pods in CrashLoopBackOff, restarts climbing.
  • kubectl logs --previous on a crashed pod — OutOfMemoryError in the first 40 lines, exit 137 in describe.
  • kubectl top pods — surviving pods near their memory limit too: a leak, not a one-off.
  • Check the deployment: memory limit unchanged for months, but today's release doubled the cache size (from the rollout history).
  • Mitigate: kubectl rollout undo to the previous revision; service recovers. Root cause goes to development with the OOM evidence attached.

Total time with this sequence: minutes. The pattern is always the same — states, previous logs, describe events, recent changes — and it works for nearly every Kubernetes incident.
