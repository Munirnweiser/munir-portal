Oracle for Production Support

The Oracle concepts and queries behind real trading-system incidents: sessions, tablespaces, blocking locks and the v$ views that expose them.

Instance vs database: the distinction that matters at 3 AM

The database is the files on disk (datafiles, redo logs, control files). The instance is the running memory plus background processes (SGA + PMON, SMON, DBWn, LGWR). When a trader says "the database is down", the first question is which one: if the instance crashed, the datafiles are fine and a restart recovers; if the storage is gone, you have a very different night ahead. Check instance status with:

SELECT instance_name, status, database_status FROM v$instance;

Status should be OPEN. Anything else — STARTED, MOUNTED — means the database is not serving applications yet.

v$ views: the database watching itself

The v$ dynamic performance views are Oracle's live telemetry. The four support analysts query most:

  • v$session — every connected session: who, from where, what it is doing, and what it is waiting on.
  • v$sql — SQL currently or recently in the shared pool, with executions and elapsed time. Your top-offenders list lives here.
  • v$process — OS processes backing the sessions.
  • v$sysstat / v$system_event — instance-wide counters and wait events.

Incident query. Sessions that are not idle, with what they are waiting for:

SELECT s.sid, s.serial#, s.username, s.program, s.status, s.event AS wait_event, s.seconds_in_wait FROM v$session s WHERE s.status = 'ACTIVE' AND s.username IS NOT NULL ORDER BY s.seconds_in_wait DESC;

If twenty sessions all wait on the same event — enq: TX - row lock contention, say — you have found your bottleneck, not twenty separate problems.

Blocking locks: who is holding whom up

One session holding a row lock while a batch job waits on it is the classic "everything is slow" root cause. This finds the chain:

SELECT blocking_session, sid AS waiting_session, seconds_in_wait, event FROM v$session WHERE blocking_session IS NOT NULL ORDER BY seconds_in_wait DESC;

The fix is rarely "kill the blocker" — the blocker is usually a legitimate long transaction. The real questions: why is the transaction open so long, and is the application committing in a loop?

Tablespace pressure: the disk-full of databases

When a tablespace hits 100%, inserts fail and the application throws errors that look like a bug but are pure capacity:

SELECT tablespace_name, ROUND(used_space * 8192 / 1024 / 1024) AS used_mb, ROUND(tablespace_size * 8192 / 1024 / 1024) AS total_mb, ROUND(used_percent, 1) AS pct_used FROM dba_tablespace_usage_metrics ORDER BY pct_used DESC;

What support watches. Alert at 85%, page at 95%. Know which tablespaces are autoextensible and which have a hard datafile limit — the fix is either adding a datafile or enabling autoextend, and only the DBA team can do it, so your job is the precise diagnosis, not the fix.

AWR and ASH: the flight recorder

AWR (Automatic Workload Repository) takes hourly snapshots of performance statistics; ASH (Active Session History) samples what every session was doing every second. After an incident, ASH answers "what exactly was the database doing at 14:32?" — top SQL, top wait events, top sessions — without anyone having been logged in at the time. For support, the takeaway is simple: when the DBA asks for the incident window, give the exact timestamps, because that is what they will query ASH against.

Reading an AWR report, section by section

After an incident, the DBA sends an AWR report covering the incident window. You do not need to read all 80 pages — read these four sections in order:

  • Load Profile — was the database actually busy? High "DB time per second" means real load; low DB time with user complaints points outside the database (network, app tier).
  • Top 10 Foreground Events — where the time went. db file sequential read is index reads (normal in OLTP); log file sync is commit waits (slow storage or over-committing); enq: TX - row lock contention is application locking.
  • SQL ordered by Elapsed Time — the specific statements responsible. One SQL at 40% of DB time is your offender; hand its SQL_ID to development.
  • Instance Efficiency — buffer cache hit ratio below ~95% in OLTP, or library cache misses, suggest memory pressure or hard parsing.

What support watches. Always compare against a baseline AWR from a healthy day. "Top event is log file sync at 12ms average" means nothing without knowing it is normally 1ms.

ASH: what is the database doing right now

AWR is history; ASH (Active Session History) samples every active session each second, so it answers "what is happening now":

SELECT event, COUNT(*) AS samples, COUNT(DISTINCT session_id) AS sessions FROM v$active_session_history WHERE sample_time >= SYSDATE - INTERVAL '15' MINUTE GROUP BY event ORDER BY samples DESC;

If the top row is db file sequential read with one SQL_ID dominating, drill into that SQL_ID in v$sql. If the top rows are all ON CPU, the database is CPU-bound — check for a runaway query, not a lock. ASH turns "the DB is slow" into a named event and a named SQL in under a minute.

RMAN: proving the backup exists

Support gets asked "are the backups good?" after every storage scare. The honest answer comes from RMAN, not from assumptions:

RMAN> LIST BACKUP SUMMARY; RMAN> CROSSCHECK BACKUP; RMAN> VALIDATE DATABASE;
  • LIST BACKUP SUMMARY — what backups exist and when they completed. A missing backup for last night is the finding.
  • CROSSCHECK — reconciles the catalog with files actually on disk; marks missing files EXPIRED so restores do not try to use them.
  • VALIDATE — reads the datafiles checking for physical corruption without restoring anything.

A backup that never gets validated is a hope, not a backup. Run the validate monthly and keep the output for audit.

Undo and redo pressure

Two classic Oracle errors are really capacity signals. ORA-01555: snapshot too old means a long-running query needed old row versions that undo has already overwritten — the undo tablespace is too small for the workload, or a huge batch is committing rarely. Check the evidence:

SELECT begin_time, end_time, ssolderrcnt, nospaceerrcnt FROM v$undostat ORDER BY begin_time DESC;

Non-zero SSOLDERRCNT confirms snapshot-too-old errors; NOSPACEERRCNT means undo ran out of space entirely. On redo: frequent log switches (check v$log_history — more than a few per hour on a busy system) mean the redo logs are too small, causing checkpoint pain and bursty I/O. Both fixes are DBA-owned, but the diagnosis — with timestamps and counters — is support's contribution.

Key takeaway. ORA-01555 is never "just retry the query." It means the undo retention does not cover the longest legitimate query, and the next long report will hit it again.
