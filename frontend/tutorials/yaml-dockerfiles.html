YAML & Dockerfiles

Two files that break deployments silently: YAML's indentation traps and Dockerfiles that build slow, fat, insecure images.

YAML gotchas that page support

YAML is whitespace-significant: two spaces per level, never tabs. The classic traps:

  • Tabs — a single tab character is a parse error; editors that "helpfully" insert tabs corrupt Kubernetes manifests and Ansible playbooks.
  • Unquoted special values — version: 1.10 parses as the float 1.1; on/yes parse as boolean true. Quote them: "1.10".
  • Anchors and aliases — &base defines a reusable block, *base references it; great for repeated env vars, dangerous when someone edits the anchor not realizing five services share it.
# BROKEN: 'ports' is a sibling of 'env' here, not a child of the container
env:
  - name: DB_HOST
    value: "db01"
ports:                      # wrong indent: belongs to the pod spec level
  - containerPort: 8080

# FIXED: ports indented under the container
        env:
          - name: DB_HOST
            value: "db01"
        ports:
          - containerPort: 8080

When a manifest "applies fine but the app misbehaves," re-read the indentation before blaming the application.

Dockerfile best practices

Each instruction creates a cached layer. Order instructions from least-frequently-changed to most: dependencies first, application code last — so a code change rebuilds only the final layers instead of reinstalling the world.

# GOOD: deps cached, code last, non-root user, multi-stage
FROM maven:3.9 AS build
WORKDIR /app
COPY pom.xml .
RUN mvn -q dependency:go-offline
COPY src ./src
RUN mvn -q package -DskipTests

FROM eclipse-temurin:17-jre
RUN useradd -m appuser
USER appuser
COPY --from=build /app/target/trading-app.jar /app.jar
ENTRYPOINT ["java","-jar","/app.jar"]

Three wins here: multi-stage keeps build tools out of the runtime image (smaller, fewer CVEs); layer ordering makes rebuilds take seconds; non-root USER limits what a container escape can do.

HEALTHCHECK: let the orchestrator know you're alive

A HEALTHCHECK instruction tells Docker how to probe the container — and Kubernetes and load balancers rely on the same idea with liveness/readiness probes. Without one, the orchestrator considers a container healthy as long as its main process hasn't exited — even if the application inside is wedged and rejecting every request.

HEALTHCHECK --interval=30s --timeout=5s --retries=3 \
  CMD curl -f http://localhost:8080/health || exit 1

Support angle: when a container is "running but the app is down," the first question is whether a health check exists and what it actually tests. A health check that only verifies the process exists will stay green through most application-level failures — make it hit a real endpoint that exercises the critical path.

Multi-line strings: | keeps lines, > folds them

YAML has two block scalars and they are not interchangeable. | (literal) preserves newlines — for scripts and config files where line breaks matter. > (folded) turns newlines into spaces — for long human-readable text. The chomping indicator controls the trailing newline: |- strips it, |+ keeps every blank line.

startup_script: |
  #!/bin/bash
  exec /app/feed --config /etc/feed.conf
# renders with real newlines: a working script

description: >
  This feed handler processes market data
  across three regions daily.
# renders as one line: "This feed handler processes
# market data across three regions daily."

command: |-
  /app/run.sh
# no trailing newline: safer for exec-form entrypoints

Support angle: a startup script written with > instead of | collapses into one line and fails cryptically at container start — when a container dies instantly with a shell syntax error, check the block scalar first.

Anchors and aliases, worked

Define once with &name, reuse with *name, and merge maps with <<: *name. The merge key is the workhorse for repeated environment blocks.

defaults: &defaults
  LOG_LEVEL: info
  TZ: Europe/Paris
  RETRIES: "3"

services:
  pricing:
    environment:
      <<: *defaults
      LOG_LEVEL: debug      # override just this one
  booking:
    environment:
      <<: *defaults    # inherits all three untouched

Two warnings from the field. First, editing the anchor changes every service that merges it — grep for *defaults before touching &defaults. Second, the merge is shallow: nested maps are replaced wholesale, not merged key-by-key, so overriding one nested key silently drops its siblings.

BuildKit cache mounts: fast builds without fat images

Dependency downloads dominate build time, and the naive fix — copying the package cache into the image — bloats every layer forever. BuildKit cache mounts persist a cache outside the image: the build reuses it, the image never contains it.

# DOCKER_BUILDKIT=1 docker build .
RUN --mount=type=cache,target=/root/.m2 \
    mvn -q package -DskipTests
RUN --mount=type=cache,target=/root/.cache/pip \
    pip install -r requirements.txt

The Maven repository and pip cache survive across builds, so rebuilds download nothing — but docker history shows no trace of them. Support angle: when CI builds are slow, check for cache mounts before rewriting the Dockerfile; and when a build mysteriously uses a stale dependency, the cache mount is the first suspect — bust it with a cache ID or a clean build.

Distroless images: smaller, safer, harder to debug

Distroless images ship only the application and its runtime — no shell, no package manager, no utilities. The payoff is real: a dramatically smaller attack surface and far fewer CVE findings in image scans. The price is paid at 3 AM: the runbook step "exec into the container and check" fails because there is no shell to exec into.

The workarounds, in order of preference: kubectl debug with an ephemeral debug container attached to the pod's namespaces; the :debug variant tags most distroless images publish (busybox shell included); and structured logging done well enough that you rarely need the shell at all. Support angle: know before the incident which images are distroless — discovering it mid-bridge-call wastes the first ten minutes.

What production support watches

  • Image pull failures — ImagePullBackOff usually means a wrong tag, a deleted image, or expired registry credentials; the Dockerfile is fine, the reference is not.
  • Tag discipline — :latest is not a version; pin digests or semantic tags so rollbacks restore the exact bytes.
  • Build context bloat — a missing .dockerignore sends gigabytes (including .git) to the daemon; slow builds are often a context problem, not a Dockerfile problem.
  • Secrets in layers — a secret copied in one layer and "deleted" in a later one is still in the image history; use build secrets or runtime injection instead.
