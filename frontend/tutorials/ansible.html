Ansible

Agentless automation for support: run one command on fifty servers, and know exactly what a failed playbook did and didn't do.

Playbooks, inventory and ad-hoc commands

Ansible connects over SSH — no agent to install. Inventory lists the target hosts (grouped: [pricing], [databases]); playbooks are YAML files declaring the desired state in tasks; ad-hoc commands run a single module without a playbook.

# ad-hoc: check disk on every app server, in parallel
ansible appservers -m shell -a "df -h /opt | tail -1"

# playbook: ensure the logrotate config exists everywhere
- hosts: appservers
  tasks:
    - name: Install logrotate config
      copy:
        src: files/app-logrotate
        dest: /etc/logrotate.d/trading-app

The ad-hoc form is the support daily driver: one command, every host, no playbook ceremony.

Idempotency: safe to re-run

Good Ansible tasks are idempotent — running them twice changes nothing the second time. Modules like copy, service and user check state first; raw shell/command tasks do not. That distinction decides whether re-running a half-failed playbook is safe: re-running idempotent tasks converges; re-running raw shell tasks can double-apply — two restarts, two config appends, two database migrations.

Triaging a failed playbook

Ansible stops at the first failed task by default and reports per host: ok, changed, failed, unreachable. Read the recap at the bottom first — it tells you which hosts failed and which never got that far.

  • unreachable — SSH problem (host down, key changed, firewall); the playbook never ran there.
  • failed on one task — everything before it applied, everything after it didn't; the fleet is now in a mixed state, so don't just re-run blindly.
  • Use --check (dry run) to preview what would change, and --limit to re-run against one host before the whole fleet.

Incident walkthrough. A playbook restarts the market-data feed on 12 servers; 9 succeed, 3 fail at the "start service" task — port already in use. The old process didn't die on those 3. Fix: kill the stale process on the 3 hosts, re-run with --limit on just those hosts, verify all 12 healthy. The mixed state was the real problem, not the restart itself.

What production support watches

  • Vault for secrets — Ansible Vault encrypts passwords and keys in playbooks; plaintext secrets in a repo are an incident waiting for an audit.
  • What changed vs what ran — the recap's changed=N count is your audit trail of what the run actually modified.
  • Partial application — a playbook that dies halfway leaves hosts inconsistent; always verify fleet-wide state after a failure, not just the failed host.
  • Privilege escalation — tasks needing root use become: yes; a task failing with "permission denied" usually just needs it added, not a new sudoers rule.
