Ansible

Agentless automation for support: run one command on fifty servers, and know exactly what a failed playbook did and didn't do.

Playbooks, inventory and ad-hoc commands

Ansible connects over SSH — no agent to install. Inventory lists the target hosts (grouped: [pricing], [databases]); playbooks are YAML files declaring the desired state in tasks; ad-hoc commands run a single module without a playbook.

# ad-hoc: check disk on every app server, in parallel
ansible appservers -m shell -a "df -h /opt | tail -1"

# playbook: ensure the logrotate config exists everywhere
- hosts: appservers
  tasks:
    - name: Install logrotate config
      copy:
        src: files/app-logrotate
        dest: /etc/logrotate.d/trading-app

The ad-hoc form is the support daily driver: one command, every host, no playbook ceremony.

Idempotency: safe to re-run

Good Ansible tasks are idempotent — running them twice changes nothing the second time. Modules like copy, service and user check state first; raw shell/command tasks do not. That distinction decides whether re-running a half-failed playbook is safe: re-running idempotent tasks converges; re-running raw shell tasks can double-apply — two restarts, two config appends, two database migrations.

Triaging a failed playbook

Ansible stops at the first failed task by default and reports per host: ok, changed, failed, unreachable. Read the recap at the bottom first — it tells you which hosts failed and which never got that far.

  • unreachable — SSH problem (host down, key changed, firewall); the playbook never ran there.
  • failed on one task — everything before it applied, everything after it didn't; the fleet is now in a mixed state, so don't just re-run blindly.
  • Use --check (dry run) to preview what would change, and --limit to re-run against one host before the whole fleet.

Incident walkthrough. A playbook restarts the market-data feed on 12 servers; 9 succeed, 3 fail at the "start service" task — port already in use. The old process didn't die on those 3. Fix: kill the stale process on the 3 hosts, re-run with --limit on just those hosts, verify all 12 healthy. The mixed state was the real problem, not the restart itself.

Roles: the directory layout that scales

Past a handful of playbooks, teams organize automation into roles — reusable units with a fixed directory structure. Ansible auto-loads each subdirectory by name, so the layout is the documentation.

roles/trading-app/
  tasks/main.yml       # the work: install, configure, start
  handlers/main.yml    # restarts, notified by tasks
  templates/          # Jinja2 templates (app.conf.j2)
  files/              # static files copied as-is
  vars/main.yml       # role variables (high precedence)
  defaults/main.yml   # safe defaults (lowest precedence)
  meta/main.yml       # dependencies on other roles

Support angle: when a value is wrong, the first question is where it was actually defined. Precedence runs: extra vars (-e) beat role vars, which beat role defaults. A "correct" default in defaults/main.yml loses silently to a stale value in vars/main.yml — check both before editing.

Handlers and notify: restart once, not twelve times

A handler is a task that runs only when notified — and only once per play, even if twelve tasks notify it. The pattern: configuration tasks notify "restart feed service"; Ansible applies all changes, then restarts the service a single time at the end.

tasks:
  - name: Deploy feed config
    template: src=feed.conf.j2 dest=/etc/feed/feed.conf
    notify: Restart feed service
  - name: Deploy feed credentials
    copy: src=feed.key dest=/etc/feed/feed.key mode=0600
    notify: Restart feed service

handlers:
  - name: Restart feed service
    service: name=feed state=restarted
# two notifies, one restart

Support angle: "config changed but the service still runs the old config" almost always means the notify line is missing — or the handler name is misspelled, in which case Ansible fails loudly. If ordering matters (migrate data before restart), call meta: flush_handlers mid-play instead of waiting for the end.

Dynamic inventory: the AWS EC2 plugin

Static inventory files rot — servers are replaced and nobody updates the list. The aws_ec2 inventory plugin queries the AWS API at run time and builds groups from instance tags, so new hosts appear automatically.

# aws_ec2.yml — inventory source, not a playbook
plugin: aws_ec2
regions: [eu-west-1]
keyed_groups:
  - key: tags.Environment
    prefix: env
  - key: tags.Role
    prefix: role
# tag Environment=prod, Role=pricing → groups env_prod, role_pricing

Support angle: the plugin authenticates with an IAM role — when the playbook suddenly sees zero hosts, check the role's EC2 read permissions and API throttling first, not the playbook. Enable the plugin's cache so every run doesn't hammer the AWS API.

Debugging become: privilege escalation failures

Tasks needing root use become: yes (default method: sudo). When escalation breaks, the error is usually one of four things:

  • "Missing sudo password" — sudo wants a password Ansible doesn't have. Fix: pass --ask-become-pass, or better, grant the service account NOPASSWD for the specific commands.
  • "user is not in the sudoers file" — the account genuinely lacks sudo rights; this is a server-build ticket, not an Ansible bug.
  • sudo requires a TTY — Defaults requiretty in sudoers breaks non-interactive SSH sessions; the fix is removing it, not working around it.
  • Wrong become user or method — become_user: oracle with become_method: su needs the target user's password, not sudo rights.

Triage in one command. ansible dbhost -b -m ping isolates escalation from everything else: if it fails, the playbook is innocent. Add -vvv to see the exact sudo command Ansible constructed — most "mysterious" become failures become obvious at that verbosity.

What production support watches

  • Vault for secrets — Ansible Vault encrypts passwords and keys in playbooks; plaintext secrets in a repo are an incident waiting for an audit.
  • What changed vs what ran — the recap's changed=N count is your audit trail of what the run actually modified.
  • Partial application — a playbook that dies halfway leaves hosts inconsistent; always verify fleet-wide state after a failure, not just the failed host.
  • Privilege escalation — tasks needing root use become: yes; a task failing with "permission denied" usually just needs it added, not a new sudoers rule.
