Git Essentials

The commands support actually uses: branching, hotfixes, conflict resolution, and recovering from mistakes without panic.

Learning path DevOps & CI/CD Track 4 of 7

Key takeaways

  • Hotfix from the production tag, not from main — main may already contain unreleased work.
  • Merge conflicts are resolved, not feared: the file shows both sides; you choose, remove the markers, commit.
  • The recovery toolkit: reflog resurrects lost commits, stash parks work, cherry-pick moves single commits, bisect finds the bad deploy.
  • Interactive rebase (pick/fixup/squash) turns a messy hotfix branch into a reviewable story.
  • git bisect finds a bad deploy in ~8 runs across 200 commits — with a hermetic pass/fail script.

The model in one minute

Git tracks snapshots, not files. Work happens on branches — movable pointers to a commit. main is the production line; feature branches diverge and come back via merge (keeps history) or rebase (rewrites history into a straight line). The golden rule: never rebase a branch someone else is using — rewriting shared history breaks everyone's clone.

git checkout -b hotfix/fix-margin-calc   # branch from main
# ... edit, test ...
git add -A && git commit -m "Fix margin calc for cleared swaps"
git push -u origin hotfix/fix-margin-calc  # open the PR / merge request

Merge conflicts: resolve, don't fear

A conflict means two branches edited the same lines. Git marks the file with <<<<<<< / ======= / >>>>>>> sections — your change on top, theirs below. Edit the file to the correct final state, remove the markers, then git add the file and git commit to finish the merge. The dangerous move is picking "mine" or "theirs" wholesale without reading both sides; in a pricing config, that silently ships the wrong parameters.

The recovery toolkit

  • Stash — git stash shelves uncommitted work so you can switch branches for an urgent fix; git stash pop brings it back.
  • Cherry-pick — git cherry-pick <commit> copies one commit onto your branch; the standard way to port a fix from main to a release branch.
  • Reflog — git reflog shows every move HEAD ever made, including "deleted" branches and bad resets. Almost nothing is truly lost: find the commit hash and git checkout -b recovery <hash>.
  • .gitignore — never commit secrets, logs, or build output; one leaked credential in history means rotating it everywhere, since history is forever.

Hotfix workflow. Production pricing is wrong and the fix is one line. Branch hotfix/ from the production tag (not from main, which may contain unreleased work), commit the fix, run the checks, merge to main and tag the release. The release tag is what the deploy pipeline picks up — if the fix isn't tagged, it isn't deployed, no matter how good the commit is.

What production support watches

  • What exactly is deployed — git log --oneline -5 and git describe --tags on the release repo answer "which commit is running in prod?" in seconds.
  • Blame before assumptions — git blame shows who last touched a broken line and when; check the commit message before paging anyone.
  • Hooks — pre-commit hooks run lint and secret scans; if a deploy fails "mysteriously," check whether a hook silently changed or blocked something.
  • Force-push is a red flag — git push --force on a shared branch rewrites teammates' history; in banks it is usually blocked by policy for good reason.

Easy

Answer: git checkout -b hotfix/fix-margin-calc <production-tag> — branch from the tag, never from main.

2. After the one-line fix, how do you commit and publish the branch?

Medium

3. A merge conflict in margin.py — resolve it step by step.

Answer: Open the file, choose one side (or combine both), delete the conflict markers, git add the file, git commit.

4. You committed to the wrong branch. Move the work without losing it.

Answer: Cherry-pick the commit onto the right branch (or stash it there), then reset the wrong branch back.

Hard

5. Use git bisect across 200 commits. How many runs, and what makes it work?

Answer: About 8 (log₂200) — it needs a hermetic pass/fail test script so each step is trustworthy.

6. After a pull, a submodule still builds the old code. Why?

Answer: Submodules don't auto-update on pull — run git submodule update; the parent repo pins the submodule pointer.

Interactive rebase: cleaning a hotfix branch

A hotfix branch with seven "wip" and "fix typo" commits is embarrassing to merge and hard to review. Interactive rebase rewrites them into a clean story before the merge — only ever on your own unshared branch:

$ git rebase -i HEAD~4
pick 9f3a1c2 Fix margin calc for cleared swaps
fixup 7b2d9e4 wip
fixup 1c8a4f0 fix typo in comment
reword 4d6b2a1 adjust threshold

fixup folds a commit into the one above and discards its message; reword lets you fix the message; squash folds but keeps both messages for editing. The result: one logical commit per logical change. Reviewers see the fix, not your keystrokes — and git bisect later works on meaningful commits instead of broken intermediate states.

git bisect: finding the bad deploy

"It worked in v2.13.0 and broke in v2.14.0" with 200 commits between is a binary search problem, and git automates it:

$ git bisect start
$ git bisect bad v2.14.0
$ git bisect good v2.13.0
$ git bisect run ./check-pricing.sh
Bisecting: 6 revisions left to test after this (roughly 3 steps)
...
9f3a1c2e4d5b6a7 is the first bad commit
$ git bisect reset

Each step checks out a midpoint commit; you (or the script) mark it good or bad, and git halves the range. With git bisect run and a script that returns 0 for good and non-zero for bad, 200 commits collapse to about 8 test runs. The script should be hermetic — build and run the specific failing check, nothing more. This is the fastest honest answer to "which change broke production?"

Submodule pitfalls

Submodules embed one repo inside another at a pinned commit — common for shared libraries and config repos. Three traps:

  • Detached HEAD is normal inside a submodule — it points at the pinned commit, not a branch. Committing there and pushing the superproject without pushing the submodule leaves everyone else with a dangling pointer.
  • Pulling the superproject does not update submodules. After every pull, run git submodule update --init --recursive, or new code silently runs against old library checkouts.
  • Forgetting to commit the pointer bump — updating the submodule locally but not committing the superproject means CI still builds the old pointer. The "fix" that works on your machine and fails in CI is usually this.

What support watches. A deploy that behaves like the old version despite a "successful" release: check whether the release repo uses submodules and whether the pointer was actually bumped in the release commit.

Large files and Git LFS

Git stores every version of every file forever, so a 500 MB model file committed three times is 1.5 GB in every clone, forever. Git LFS (Large File Storage) stores a tiny pointer in the repo and the real bytes on a separate server:

$ git lfs install
$ git lfs track "*.h5"
$ git lfs track "models/**"
$ git add .gitattributes   # the tracking rules ARE versioned

Symptoms of LFS trouble: clones that take 40 minutes (binaries in history), or CI failing with "pointer file" errors because the runner lacks LFS or the LFS server is unreachable. Track binary types from day one — retrofitting LFS onto a repo with gigabytes of history requires rewriting history, which on a shared repo is a coordinated event, not a casual command.

Key takeaway. Repos get slow for exactly two reasons: too much history or too-big files. git count-objects -vH tells you which one in seconds.
