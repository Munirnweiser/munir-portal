Docker for Production Support

The Docker knowledge that actually gets used on shift: what is running, why it died, where its logs are, and how to clean up safely.

Images vs containers: the one distinction

An image is the read-only blueprint (your application plus its runtime, built from a Dockerfile). A container is a running instance of that image. Deleting a container does not delete the image; deleting the image does not stop running containers — but you cannot delete an image while a container still references it. That dependency order is the source of half of all Docker cleanup confusion:

docker ps # running containers docker ps -a # including stopped ones docker images # local images docker inspect <name> # full JSON: mounts, env, network, health

The triage sequence for a dead container

When a service container is down, run these in order before touching anything:

docker ps -a --filter "name=trade-api" # what state is it in? Exited (1)? OOMKilled? docker logs --tail 100 trade-api # last 100 lines: the actual error docker logs --since 30m trade-api # only the incident window docker stats --no-stream # CPU/mem per container right now

The exit code tells the story: 137 means killed by OOM (out of memory — check the memory limit), 1 means the application itself exited with an error (read the logs), 125/126/127 mean Docker-level failures (bad flags, permission, command not found).

What support watches. A container restarting every few minutes with exit code 137 and climbing memory in docker stats is a memory leak hitting its cgroup limit. The short-term fix is raising the limit or restarting; the long-term fix belongs to development. Document the pattern either way.

Getting inside: exec and copying files

docker exec -it trade-api sh # shell inside the running container docker exec trade-api env | sort # environment variables it actually sees docker cp trade-api:/app/logs/app.log ./ # pull a log file out for analysis

Note the environment check: most "it works on my machine" container bugs are a missing or wrong environment variable inside the container, not a code bug. Compare docker exec ... env against the deployment manifest.

Volumes and networks: where data and traffic live

Containers are ephemeral — anything written to the container filesystem disappears when it is removed. Persistent data lives in volumes or bind mounts. If a database container lost its data after a recreate, the volume was not mounted: docker inspect shows the mounts, and an empty mounts list on a stateful service is the finding.

On networking: containers on the default bridge network reach each other by IP but not by name; user-defined networks give DNS by container name. "Connection refused between services" is very often two containers on different networks, or the target listening on localhost inside its own container instead of 0.0.0.0.

Cleanup without tears

docker container prune # remove STOPPED containers only docker image prune # remove dangling (untagged) images only docker image prune -a # remove ALL unused images — careful on shared hosts docker volume prune # remove unused volumes — DATA LOSS risk, confirm first docker system df # what is actually consuming disk

"No space left on device" on a Docker host is almost always old images and stopped containers. Run docker system df first so you clean what is actually big, and never prune volumes on a host carrying a database you have not backed up.
