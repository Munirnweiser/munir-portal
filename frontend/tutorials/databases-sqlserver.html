SQL Server for Production Support

The DMVs and checks behind SQL Server incidents: what is running now, what is blocked, which job failed, and where the server is spending its time.

Learning path Databases Track 3 of 3
← Previous All tracks

Key takeaways

  • DMVs show what the server is doing right now — sys.dm_exec_requests is your live dashboard.
  • Blocking chains resolve top-down: find the head blocker; everything downstream clears when it does.
  • Deadlock 1205 picks a victim by priority and cost — fix the access order, and make apps retry.
  • Query Store catches plan regressions — sp_query_store_force_plan pins the last good plan.
  • Tempdb PAGELATCH on 2:1:1/2/3 means add files; fragmentation above 30% means rebuild the index.

DMVs: asking the server what it is doing

Dynamic Management Views are SQL Server's live telemetry — the equivalent of Oracle's v$ views. The essential triage query shows every executing request with its wait:

SELECT r.session_id, s.login_name, s.program_name, r.status, r.command, r.wait_type, r.wait_time, t.text AS sql_text FROM sys.dm_exec_requests r JOIN sys.dm_exec_sessions s ON r.session_id = s.session_id CROSS APPLY sys.dm_exec_sql_text(r.sql_handle) t WHERE r.session_id > 50 ORDER BY r.wait_time DESC;

The wait_type column is the diagnosis: LCK_M_X means blocked on a lock, PAGEIOLATCH_SH means waiting on disk I/O, CXPACKET points at parallelism. Read the wait type before anything else.

Blocking chains: finding the head blocker

sys.dm_exec_requests.blocking_session_id tells you who each session waits on. The head blocker is the session with a non-zero value in others' rows but zero in its own — it is not waiting, everyone else waits on it:

SELECT session_id, blocking_session_id, wait_type, wait_time, last_wait_type FROM sys.dm_exec_requests WHERE blocking_session_id <> 0 OR session_id IN (SELECT DISTINCT blocking_session_id FROM sys.dm_exec_requests WHERE blocking_session_id <> 0);

What support watches. A blocking chain that grows during the end-of-day batch usually means an uncommitted transaction — an application bug holding a lock open across a long loop. The head blocker's sql_text and program_name identify the culprit process to escalate.

Deadlocks: the error 1205

A deadlock is two sessions each holding a lock the other wants; SQL Server picks a victim and kills it with error 1205. Unlike blocking, you cannot wait it out. The deadlock graph in the SQL Server error log (or Extended Events) shows the two statements and their lock order. Support's role: capture the victim's query and timestamp, identify the pattern (two processes updating the same tables in opposite order is the classic), and hand it to development — the fix is consistent lock ordering or shorter transactions, not a server setting.

SQL Agent jobs: the batch that did not run

End-of-day pricing, reconciliations and report loads usually run as SQL Agent jobs. When downstream data is missing, check job history before assuming a database problem:

SELECT j.name AS job_name, h.step_name, h.run_status, msdb.dbo.agent_datetime(h.run_date, h.run_time) AS run_ts, h.message FROM msdb.dbo.sysjobs j JOIN msdb.dbo.sysjobhistory h ON j.job_id = h.job_id WHERE msdb.dbo.agent_datetime(h.run_date, h.run_time) >= DATEADD(HOUR, -12, GETDATE()) AND h.run_status <> 1 ORDER BY run_ts DESC;

run_status 0 = failed, 2 = retry, 3 = cancelled. The message column usually names the failing step. Also verify the SQL Server Agent service itself is running — a stopped Agent means no jobs ran, and every downstream alert fires at once.

Wait stats and backups: the two health checks

sys.dm_os_wait_stats aggregated since the last restart shows where the server spends its waiting time. A sudden spike in PAGEIOLATCH_* means the storage layer is struggling; LCK_* spikes mean concurrency pain. Compare against a known-good baseline, not against zero.

And the check nobody runs until it is too late — when was the last successful backup?

SELECT d.name AS database_name, MAX(b.backup_finish_date) AS last_backup FROM sys.databases d LEFT JOIN msdb.dbo.backupset b ON d.name = b.database_name GROUP BY d.name ORDER BY last_backup;

A production database with no recent backup turns every incident into a potential data-loss incident. Verify this before the crisis.

Query Store: catching plan regressions

A query that ran fine for months suddenly takes ten times longer after a statistics update or a data growth spurt — the plan changed. Query Store keeps the history of plans per query, so you can prove the regression and revert it:

SELECT q.query_id, qt.query_sql_text, rs.avg_duration, rs.avg_cpu_time, rs.count_executions FROM sys.query_store_query q JOIN sys.query_store_query_text qt ON q.query_text_id = qt.query_text_id JOIN sys.query_store_plan p ON q.query_id = p.query_id JOIN sys.query_store_runtime_stats rs ON p.plan_id = rs.plan_id WHERE rs.last_execution_time > DATEADD(HOUR, -2, GETDATE()) ORDER BY rs.avg_duration DESC;

In SSMS, open Query Store → Regressed Queries for the visual version: it shows the old plan and the new plan side by side with their runtimes. The emergency fix is forcing the last good plan:

EXEC sp_query_store_force_plan @query_id = 42, @plan_id = 17;

That buys time while development fixes the root cause (usually stale statistics or a parameter-sniffing issue). Unforce with sp_query_store_unforce_plan once the real fix is in.

What support watches. A "slow since this morning's deploy" ticket where the code did not change is a plan regression until proven otherwise — check Query Store before blaming the release.

Always On: failover readiness checks

Trading databases usually run in an Always On availability group. When the primary has a problem, you need to know before the failover whether the secondary can actually take over:

SELECT ag.name AS ag_name, ar.replica_server_name, ar.availability_mode_desc, rs.role_desc, rs.synchronization_state_desc, rs.synchronization_health_desc FROM sys.availability_groups ag JOIN sys.availability_replicas ar ON ag.group_id = ar.group_id JOIN sys.dm_hadr_availability_replica_states rs ON ar.replica_id = rs.replica_id;
  • synchronization_state_desc should be SYNCHRONIZED on synchronous replicas — SYNCHRONIZING means the secondary is behind and a failover would lose data or take long.
  • synchronization_health_desc NOT_HEALTHY is a page-level alert, not a wait-and-see.
  • Verify the listener DNS name resolves and points at the current primary — applications connect to the listener, and a stale DNS cache after failover looks exactly like "the database is down."

Tempdb contention: the PAGELATCH storm

Tempdb is shared by every query doing sorts, hashes, and temp tables. When allocation pages become a hotspot, waits show up as PAGELATCH_UP on pages 2:1:1, 2:1:2, 2:1:3 (the PFS, GAM and SGAM pages of tempdb):

SELECT wait_type, waiting_tasks_count, wait_time_ms / 1000.0 AS wait_sec FROM sys.dm_os_wait_stats WHERE wait_type LIKE 'PAGELATCH%';

The standard fix is multiple tempdb data files — one per CPU core up to 8 — so allocations spread across pages, plus trace flags 1118/1117 on older versions (default behavior since 2016). Support's tell: PAGELATCH waits that spike exactly when the overnight batch runs and vanish afterwards. That pattern means tempdb sizing, not a bad query.

Index fragmentation: rebuild or reorganize

Fragmentation grows with every insert/update/delete cycle. Measure it first:

SELECT OBJECT_NAME(ips.object_id) AS table_name, i.name AS index_name, ips.avg_fragmentation_in_percent FROM sys.dm_db_index_physical_stats(DB_ID(), NULL, NULL, NULL, 'LIMITED') ips JOIN sys.indexes i ON ips.object_id = i.object_id AND ips.index_id = i.index_id WHERE ips.avg_fragmentation_in_percent > 5 ORDER BY ips.avg_fragmentation_in_percent DESC;

The maintenance rule: below 5% do nothing; 5–30% ALTER INDEX ... REORGANIZE (online, light); above 30% ALTER INDEX ... REBUILD (heavier, can be online in Enterprise). A trade table rebuilt weekly that suddenly shows 90% fragmentation after one night means something did a massive delete/insert cycle — find the job before rebuilding, or you will rebuild again tomorrow.

Key takeaway. Fragmentation is a symptom schedule, not a one-time fix. If the numbers return within days, the write pattern is the problem, not the index.
