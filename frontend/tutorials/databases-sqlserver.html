SQL Server for Production Support

The DMVs and checks behind SQL Server incidents: what is running now, what is blocked, which job failed, and where the server is spending its time.

DMVs: asking the server what it is doing

Dynamic Management Views are SQL Server's live telemetry — the equivalent of Oracle's v$ views. The essential triage query shows every executing request with its wait:

SELECT r.session_id, s.login_name, s.program_name, r.status, r.command, r.wait_type, r.wait_time, t.text AS sql_text FROM sys.dm_exec_requests r JOIN sys.dm_exec_sessions s ON r.session_id = s.session_id CROSS APPLY sys.dm_exec_sql_text(r.sql_handle) t WHERE r.session_id > 50 ORDER BY r.wait_time DESC;

The wait_type column is the diagnosis: LCK_M_X means blocked on a lock, PAGEIOLATCH_SH means waiting on disk I/O, CXPACKET points at parallelism. Read the wait type before anything else.

Blocking chains: finding the head blocker

sys.dm_exec_requests.blocking_session_id tells you who each session waits on. The head blocker is the session with a non-zero value in others' rows but zero in its own — it is not waiting, everyone else waits on it:

SELECT session_id, blocking_session_id, wait_type, wait_time, last_wait_type FROM sys.dm_exec_requests WHERE blocking_session_id <> 0 OR session_id IN (SELECT DISTINCT blocking_session_id FROM sys.dm_exec_requests WHERE blocking_session_id <> 0);

What support watches. A blocking chain that grows during the end-of-day batch usually means an uncommitted transaction — an application bug holding a lock open across a long loop. The head blocker's sql_text and program_name identify the culprit process to escalate.

Deadlocks: the error 1205

A deadlock is two sessions each holding a lock the other wants; SQL Server picks a victim and kills it with error 1205. Unlike blocking, you cannot wait it out. The deadlock graph in the SQL Server error log (or Extended Events) shows the two statements and their lock order. Support's role: capture the victim's query and timestamp, identify the pattern (two processes updating the same tables in opposite order is the classic), and hand it to development — the fix is consistent lock ordering or shorter transactions, not a server setting.

SQL Agent jobs: the batch that did not run

End-of-day pricing, reconciliations and report loads usually run as SQL Agent jobs. When downstream data is missing, check job history before assuming a database problem:

SELECT j.name AS job_name, h.step_name, h.run_status, msdb.dbo.agent_datetime(h.run_date, h.run_time) AS run_ts, h.message FROM msdb.dbo.sysjobs j JOIN msdb.dbo.sysjobhistory h ON j.job_id = h.job_id WHERE msdb.dbo.agent_datetime(h.run_date, h.run_time) >= DATEADD(HOUR, -12, GETDATE()) AND h.run_status <> 1 ORDER BY run_ts DESC;

run_status 0 = failed, 2 = retry, 3 = cancelled. The message column usually names the failing step. Also verify the SQL Server Agent service itself is running — a stopped Agent means no jobs ran, and every downstream alert fires at once.

Wait stats and backups: the two health checks

sys.dm_os_wait_stats aggregated since the last restart shows where the server spends its waiting time. A sudden spike in PAGEIOLATCH_* means the storage layer is struggling; LCK_* spikes mean concurrency pain. Compare against a known-good baseline, not against zero.

And the check nobody runs until it is too late — when was the last successful backup?

SELECT d.name AS database_name, MAX(b.backup_finish_date) AS last_backup FROM sys.databases d LEFT JOIN msdb.dbo.backupset b ON d.name = b.database_name GROUP BY d.name ORDER BY last_backup;

A production database with no recent backup turns every incident into a potential data-loss incident. Verify this before the crisis.
