SQL for Production Support

The queries that actually get run during incidents: filtering trade data, joining it to reference data, and spotting the anomaly before the trader does.

SELECT with intent: filter first, join second

In support you rarely query whole tables. You start from a symptom — a trade ID, a book, a time window — and you filter hard before you join anything. A typical first query during a booking incident:

SELECT trade_id, book, status, ccy_pair, notional, created_ts FROM trades WHERE created_ts >= SYSDATE - INTERVAL '2' HOUR AND status = 'PENDING' ORDER BY created_ts DESC FETCH FIRST 50 ROWS ONLY;

Only after the suspect rows are isolated do you join to reference data (counterparties, books, static data). Joining first and filtering later is how a "quick check" becomes a full table scan that pages the DBA.

JOINs: the three you use daily

  • INNER JOIN — trades to their static data. Rows without a match are dropped, which is exactly what you want when hunting orphaned records.
  • LEFT JOIN — master to detail, e.g. all orders and their fills. Orders with no fills show NULLs: those are your unexecuted orders.
  • Self join — comparing a row to another row in the same table, e.g. a trade and its amendment history.

What support watches. A LEFT JOIN from orders to executions where the execution side is NULL, filtered to the last hour, is the fastest way to answer "did my orders actually reach the market?"

Aggregations: counting what is broken

GROUP BY turns a million-row mess into a five-line answer:

SELECT status, COUNT(*) AS n, SUM(notional) AS total_notional FROM trades WHERE trade_date = TRUNC(SYSDATE) GROUP BY status HAVING COUNT(*) > 0 ORDER BY n DESC;

Run this on settlement-date trades and you instantly see how many are stuck in each state — the same shape as an STP-rate dashboard, built ad hoc in thirty seconds.

Window functions: queue and spike analysis

When a feed slows down, you need row-by-row context, not just totals. LAG() compares each event to the previous one:

SELECT event_ts, LAG(event_ts) OVER (ORDER BY event_ts) AS prev_ts, EXTRACT(SECOND FROM (event_ts - LAG(event_ts) OVER (ORDER BY event_ts))) AS gap_sec FROM market_data_events WHERE symbol = 'EURUSD' AND event_ts >= SYSDATE - INTERVAL '1' HOUR;

Sort by gap_sec descending and the feed gaps jump out. ROW_NUMBER() OVER (PARTITION BY trade_id ORDER BY version DESC) is the standard trick for keeping only the latest version of an amended trade.

Reading an execution plan

A slow query is a plan problem. The two things to read first:

  • Access path — is it using the index you expect, or doing a FULL TABLE SCAN? A full scan on a billion-row trade history table is your smoking gun.
  • Cardinality estimates vs actuals — if the optimizer expected 10 rows and got 10 million, the statistics are stale and the plan is wrong.

Slow-query triage checklist. 1) Is there a missing index on the filter/join columns? 2) Are statistics stale (last analyzed date)? 3) Is a function wrapping an indexed column (TRUNC(created_ts) kills index use — use a range instead)? 4) Is the query pulling columns it never displays? Fix these four before escalating.
