Practice: easy, medium, hard

Try these before moving on — click a question to reveal the answer.

Easy

1. Write the 'did my orders reach the market in the last hour' check.

Answer: SELECT o.* FROM orders o LEFT JOIN executions e ON e.order_id = o.order_id WHERE e.order_id IS NULL AND o.created_ts > now() - interval '1 hour';

2. Why is WHERE TRUNC(created_ts) = TRUNC(SYSDATE) bad?

Answer: The function wraps the indexed column, so the index can't be used — use created_ts >= TRUNC(SYSDATE) AND created_ts < TRUNC(SYSDATE)+1 instead.

Medium

3. Sketch gap-and-island sessionization of logins with 30-minute gaps.

Answer: Use LAG(login_ts) to flag rows where the gap exceeds 30 minutes, then a running SUM() over the flag to assign session ids.

4. Recite the slow-query triage checklist in order.

Answer: 1) Missing index on filter/join columns → 2) stale statistics → 3) function wrapping an indexed column → 4) bad execution plan.

Hard

5. Nested loops vs hash join: when does the optimizer pick wrong, and what's the fix?

Answer: Stale statistics or bind peeking mislead cardinality estimates; fix with fresh stats, histograms, or a plan baseline.

6. A deadlock trace lands in the alert log. What do you extract from it?

Answer: The two sessions, the objects/rows each held and wanted, and the access order — then fix the ordering or shorten the transactions.

SQL for Production Support

The queries that actually get run during incidents: filtering trade data, joining it to reference data, and spotting the anomaly before the trader does.

Learning path Databases Track 1 of 3
All tracks Next →

Key takeaways

  • Filter first, join second — shrink the row set before the expensive join, not after.
  • The fastest market-reach check: LEFT JOIN orders to executions and filter WHERE the execution side IS NULL.
  • Window functions turn events into sessions — LAG plus a running SUM implements gap-and-island sessionization.
  • TRUNC(created_ts) kills index use — always use a date range instead.
  • Amendment chains longer than 3 versions/day on one trade mean the upstream feed is flapping — fix the feed, not the trades.

SELECT with intent: filter first, join second

In support you rarely query whole tables. You start from a symptom — a trade ID, a book, a time window — and you filter hard before you join anything. A typical first query during a booking incident:

SELECT trade_id, book, status, ccy_pair, notional, created_ts FROM trades WHERE created_ts >= SYSDATE - INTERVAL '2' HOUR AND status = 'PENDING' ORDER BY created_ts DESC FETCH FIRST 50 ROWS ONLY;

Only after the suspect rows are isolated do you join to reference data (counterparties, books, static data). Joining first and filtering later is how a "quick check" becomes a full table scan that pages the DBA.

JOINs: the three you use daily

  • INNER JOIN — trades to their static data. Rows without a match are dropped, which is exactly what you want when hunting orphaned records.
  • LEFT JOIN — master to detail, e.g. all orders and their fills. Orders with no fills show NULLs: those are your unexecuted orders.
  • Self join — comparing a row to another row in the same table, e.g. a trade and its amendment history.

What support watches. A LEFT JOIN from orders to executions where the execution side is NULL, filtered to the last hour, is the fastest way to answer "did my orders actually reach the market?"

Aggregations: counting what is broken

GROUP BY turns a million-row mess into a five-line answer:

SELECT status, COUNT(*) AS n, SUM(notional) AS total_notional FROM trades WHERE trade_date = TRUNC(SYSDATE) GROUP BY status HAVING COUNT(*) > 0 ORDER BY n DESC;

Run this on settlement-date trades and you instantly see how many are stuck in each state — the same shape as an STP-rate dashboard, built ad hoc in thirty seconds.

Window functions: queue and spike analysis

When a feed slows down, you need row-by-row context, not just totals. LAG() compares each event to the previous one:

SELECT event_ts, LAG(event_ts) OVER (ORDER BY event_ts) AS prev_ts, EXTRACT(SECOND FROM (event_ts - LAG(event_ts) OVER (ORDER BY event_ts))) AS gap_sec FROM market_data_events WHERE symbol = 'EURUSD' AND event_ts >= SYSDATE - INTERVAL '1' HOUR;

Sort by gap_sec descending and the feed gaps jump out. ROW_NUMBER() OVER (PARTITION BY trade_id ORDER BY version DESC) is the standard trick for keeping only the latest version of an amended trade.

Reading an execution plan

A slow query is a plan problem. The two things to read first:

  • Access path — is it using the index you expect, or doing a FULL TABLE SCAN? A full scan on a billion-row trade history table is your smoking gun.
  • Cardinality estimates vs actuals — if the optimizer expected 10 rows and got 10 million, the statistics are stale and the plan is wrong.

Slow-query triage checklist. 1) Is there a missing index on the filter/join columns? 2) Are statistics stale (last analyzed date)? 3) Is a function wrapping an indexed column (TRUNC(created_ts) kills index use — use a range instead)? 4) Is the query pulling columns it never displays? Fix these four before escalating.

Sessionization: turning events into sessions

Traders log in and out all day; support questions are about sessions, not raw logins. The gap-and-island pattern groups events into sessions whenever the gap exceeds a threshold — here 30 minutes:

WITH ordered AS ( SELECT trader_id, login_ts, LAG(login_ts) OVER (PARTITION BY trader_id ORDER BY login_ts) AS prev_ts FROM trader_logins ), flagged AS ( SELECT trader_id, login_ts, CASE WHEN prev_ts IS NULL OR login_ts - prev_ts > INTERVAL '30' MINUTE THEN 1 ELSE 0 END AS new_session FROM ordered ) SELECT trader_id, SUM(new_session) OVER (PARTITION BY trader_id ORDER BY login_ts) AS session_id, login_ts FROM flagged ORDER BY trader_id, login_ts;

LAG() finds the previous login; the CASE flags session starts; the running SUM() turns flags into session numbers. Logins at 09:00, 09:12 and 09:55 become sessions 1, 1, 2. This is the same technique used to sessionize FIX connections when a client reconnects repeatedly — each reconnect cluster is one "session" for the incident timeline.

Hierarchical queries: following amendment chains

A trade amended five times is a chain, not five independent rows. Oracle's CONNECT BY walks the chain in one query:

SELECT trade_id, amends_trade_id, LEVEL AS depth FROM trades START WITH trade_id = 'T-88412' CONNECT BY PRIOR amends_trade_id = trade_id;

This returns the original trade plus every amendment in order. During a booking dispute — "which version did the client actually confirm?" — this query gives the full lineage instead of five separate lookups. The portable alternative is a recursive CTE (WITH RECURSIVE), supported by PostgreSQL and Oracle 11gR2+.

What support watches. Amendment chains longer than 3 versions on the same trade in one day usually mean an upstream system is flapping — fix the feed, not the trades.

Index design for trade tables

Trade tables are huge and queried by the same few patterns, so index column order matters. Rules of thumb:

  • Equality columns first, range columns last. CREATE INDEX trades_book_date_idx ON trades(book, trade_date, status); serves WHERE book = 'EQ' AND trade_date >= ... perfectly; reversing the order would not.
  • Covering indexes — if the index contains every column the query selects, the database never touches the table. For a dashboard query run every minute, that is the difference between milliseconds and seconds.
  • Never wrap an indexed column in a function. WHERE TRUNC(trade_date) = ... disables the index; use a range instead: WHERE trade_date >= TRUNC(SYSDATE) AND trade_date < TRUNC(SYSDATE)+1.

Support rarely creates indexes — that is a DBA change — but identifying the missing index in the incident report ("filter on book+trade_date does a full scan; composite index would fix it") is exactly what gets the change approved fast.

Reading deadlocks in the logs

When Oracle detects a deadlock it writes ORA-00060: deadlock detected to the alert log and dumps a deadlock graph to a trace file. The graph lists the two sessions, the SQL each was running, and the exact rows (by rowid) they fought over. Support's job:

  • Capture the trace file name and timestamp from the alert log — DBAs will ask for it.
  • Identify the two statements. If it is the same pair every night at 02:00, it is a batch-schedule collision, not a mystery.
  • Check whether one side is a long-running report holding locks it does not need — read-consistency means readers should not block writers; a blocking reader is often missing an index or doing an unnecessary SELECT ... FOR UPDATE.

Key takeaway. Deadlocks are an application design signal. Your incident report should name the two statements and their lock order — that is what development needs to fix it with consistent ordering or shorter transactions.

Reading an execution plan

When a query is slow, read its plan before touching anything. The plan is the optimizer telling you what it decided. The two join strategies that matter most:

-- trade blotter: 40 rows from ORDERS, 2M rows in TRADES EXPLAIN SELECT o.id, t.price FROM orders o JOIN trades t ON t.order_id = o.id WHERE o.trade_date = CURRENT_DATE; -- plan (simplified): -- NESTED LOOP -- -> Index Range Scan on orders(trade_date) -- 40 rows -- -> Index Lookup on trades(order_id) -- ~3 rows per order

Nested loops win when the outer side is small and the inner side has an index - 40 probe lookups, done. Hash join wins when both sides are large: build a hash table on the smaller side, scan the bigger side once. Rule of thumb: small x indexed goes nested loops; large x large goes hash join.

-- red flag: the same query, a different plan after a data growth spurt -- HASH JOIN -- -> Seq Scan on trades -- 2M rows, no usable index! -- -> Hash on orders -- diagnosis: the trades(order_id) index was dropped during a migration. -- fix: recreate the index, re-gather stats, re-check the plan.

When the optimizer picks wrong

Plans change without anyone touching the query. The usual culprits:

  • Stale statistics - the optimizer thinks a table has 10k rows; it has 10M. Regather stats and watch the plan flip back.
  • Bind-variable peeking - the plan was optimized for the first parameter value seen, which was an outlier. Sudden slowness right after a deploy or restart is the signature.
  • Missing histograms - skewed columns (status flags, desk codes) need histograms, or the cardinality estimates are fiction.

Support discipline: capture the good plan (baseline / stored outline) before you need it, so "the query got slow overnight" becomes a ten-minute compare-and-restore instead of a war room. Hints are the last resort, not the first - fix the inputs (stats, indexes) before overriding the optimizer.
