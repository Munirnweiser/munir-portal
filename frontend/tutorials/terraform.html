Terraform

Infrastructure as code for support: reading plans, understanding state, and untangling the two classic failures — locks and drift.

Resources, state and plans

Terraform manages resources (VMs, databases, networks) declared in .tf files. The state file records what Terraform believes exists; terraform plan compares desired configuration against state and reality, then prints the diff; terraform apply executes it.

$ terraform plan
  # aws_instance.pricing_engine will be updated in-place
  ~ instance_type = "m5.xlarge" -> "m5.2xlarge"
  # aws_db_instance.riskdb will be replaced
  -/+ engine_version = "14.5" -> "15.2" (forces replacement)

Plan: 1 to add, 1 to change, 1 to destroy.

Learn to read this output like a release note: + creates, - destroys, ~/ updates in place, -/+ destroys and recreates. A -/+ on a database means downtime and data migration — that line deserves a change ticket, not a casual apply.

State locks: the pipeline is stuck

State is shared, so Terraform locks it during runs. If a run crashes mid-apply, the lock can stick and every later run fails with "Error acquiring the state lock." First check whether a run is genuinely still active; if the holder is dead, terraform force-unlock <lock-id> releases it. The support discipline: never force-unlock while another apply might be running — two writers corrupt state, and corrupted state means Terraform no longer knows what exists.

Drift: reality diverged from code

Drift is when someone changes infrastructure by hand — a bigger VM sized up in the console during an incident, a firewall rule added for debugging. The next plan suddenly wants to "fix" those manual changes back, which can undo the very thing keeping production alive.

Incident walkthrough. During a market-data outage, an engineer manually doubled the feed handler's instance size in the cloud console. A week later, a routine plan proposes shrinking it back — applying it would re-create the outage. The correct sequence: import the reality into the configuration (or update the .tf to match), then plan clean. Rule of thumb: the console is for reading during incidents; all changes go through code afterwards.

Import: bringing hand-built infrastructure under management

Sometimes infrastructure already exists — built by hand before Terraform was adopted. terraform import maps an existing real-world resource to a resource block, after which Terraform manages it like any other. The workflow: write the resource block to match reality as closely as you can, run terraform import aws_instance.pricing_engine i-0abcd1234, then run terraform plan — it should show no changes. If the plan wants to modify things, adjust the configuration until it is clean; only then is the import safe. Support relevance: after an incident where someone built emergency infrastructure by hand, importing it (rather than leaving it unmanaged) prevents the next plan from trying to delete it.

What production support watches

  • Plan before apply, always — a plan with unexpected destroys is a stopped deployment, not a puzzle to solve by applying and hoping.
  • State backend health — state lives in remote storage (S3, Terraform Cloud); if that storage is unreachable, no infrastructure change can run at all.
  • Rollback = previous known-good apply — keep prior plans; rolling back means applying the last good configuration, and knowing which commit that was.
  • Secrets stay out — state files can contain secrets in plaintext; they must be encrypted at rest and never committed to git.

Module version pinning

Calling a module without a version means "whatever is newest" — and newest can be a breaking major release:

module "vpc" {
  source  = "terraform-aws-modules/vpc/aws"
  version = "~> 5.1"
}

~> 5.1 allows 5.1.x patch updates but never 6.0. An unpinned module that jumps a major version can rename outputs, change defaults, or force resource replacement — discovered at apply time, in production. The support angle: when a previously green pipeline suddenly plans destroys nobody asked for, git log the module version pins first. The lock file (.terraform.lock.hcl) records exact provider versions per environment; commit it, and diff it when plans surprise you.

Remote state backends: S3 with locking

State in git is corruption waiting to happen (plus secrets in plaintext). Production Terraform keeps state in remote storage with locking so two applies can never write at once:

terraform {
  backend "s3" {
    bucket         = "bank-tfstate-prod"
    key            = "trading/terraform.tfstate"
    region         = "eu-west-1"
    dynamodb_table = "tfstate-locks"
    encrypt        = true
  }
}

The DynamoDB table provides the lock; encrypt = true keeps secrets in state unreadable at rest. When every apply fails with "bucket not found" or "access denied," the state backend itself is down or the credentials expired — no infrastructure change can run until it is healthy, so the backend is the first thing to check, not the last.

Taint and replace: the sick VM

Sometimes a resource is unhealthy but the configuration is correct — a VM with a corrupted disk, a node that will not come back. Editing config will not help; the resource itself must be recreated. The old command was terraform taint; the modern form is a flag on apply:

$ terraform apply -replace=aws_instance.pricing_engine

The next plan shows that one resource as -/+ (destroy then create) and nothing else changes. This is the disciplined alternative to deleting things in the console: the replacement is recorded, reviewed, and repeatable. Never use replace on stateful resources (databases!) without a backup and a maintenance window — recreating a database from scratch is data loss unless the restore is planned.

Cost estimation before apply

A plan that adds twenty m5.2xlarge instances is a budget incident as well as a technical change. Cost-estimation tools annotate the plan with the monthly delta:

$ infracost diff --path .
  + aws_instance.pricing_engine (m5.xlarge -> m5.2xlarge)
    +$280/mo  (~$3,360/yr)

Banks gate expensive plans on approval tickets; support's role is reading the cost section of the plan review, not just the resource counts. A "routine" apply that doubles the monthly bill gets stopped at the change advisory board if someone actually reads the estimate — make sure that someone is you.

Key takeaway. Every Terraform change has three reviews: correctness (does the plan do what we want?), safety (any unexpected destroys?), and cost (can we afford it?). Skipping any one of them is how incidents and budget surprises happen.
