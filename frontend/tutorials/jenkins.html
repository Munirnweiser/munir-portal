The build server behind most bank deployments: pipelines, agents, logs — and how support triages a failed release at 2 AM.

How Jenkins is organized

Jenkins has a controller (the web UI, job definitions, scheduling) and agents (workers that actually run builds). Work is defined in pipelines — a Jenkinsfile checked into the repo — split into stages (Checkout → Build → Test → Deploy) made of steps. Blue Ocean renders the pipeline as a visual flow where each stage is green, red, or still running.

pipeline {
  agent { label 'linux-build' }
  stages {
    stage('Checkout') { steps { checkout scm } }
    stage('Build')    { steps { sh 'mvn -q package -DskipTests' } }
    stage('Test')     { steps { sh 'mvn test' } }
    stage('Deploy')   { steps { sh './deploy.sh staging' } }
  }
}

Declarative pipelines like this are the bank standard: the whole release process is code, reviewed and versioned like everything else.

Reading a failed build

When a deployment fails, open the build → Console Output. Read bottom-up: the last 50 lines hold the actual error; everything above is context. The pattern that matters:

  • Compilation/test failure — red in the Test stage; the code is broken, page the dev team, not support.
  • Agent offline — build never starts, "waiting for next available executor"; the agent node is down or disconnected.
  • Timeout in Deploy — the deploy script hung; check whether it partially deployed before killing it, or you get half a release.
  • Credential errors — "invalid credentials" or 401 pushing artifacts; the service account password rotated and nobody updated Jenkins.

Support actions: restart, abort, roll back

Restart from stage re-runs only the failed stage — use it when the failure was environmental (agent hiccup, flaky test), not when the code is broken. Abort stops a hung build, but first verify what it already did: an aborted deploy mid-copy leaves inconsistent binaries. For rollbacks, banks keep the previous artifact — redeploy the last green build's artifact rather than "reverting code and rebuilding," which is slower and riskier.

Incident walkthrough. 2:10 AM: the pricing-engine deploy goes red at the Deploy stage — "connection refused" to the target host. Console shows the SSH step failing. Check: the target server is up (ping works), but the deploy user can't log in — its key was rotated at midnight. Fix: update the Jenkins credential, restart from the Deploy stage, confirm the health check turns green. Total downtime 25 minutes, and the root cause goes in the incident report, not just "restarted Jenkins."

What production support watches

  • Credential hygiene — rotated passwords and expired certificates are the #1 cause of "Jenkins is broken" tickets; the fix is in the credentials store, not the pipeline.
  • Agent capacity — a queue of builds with no free executors means agents are down or undersized; releases pile up behind each other.
  • Artifact traceability — every production deploy must map to a build number and a git commit; if it doesn't, the audit trail is broken.
  • Never "just rebuild" — rebuilding masks flaky failures; read the console output first, then decide whether a restart is safe.

Shared libraries: one pipeline definition, two hundred users

Banks do not copy-paste Jenkinsfiles into every repo — they keep a shared library of pipeline steps, and each service calls it in a few lines:

@Library('bank-pipeline-lib@1.4.0') _
standardJavaPipeline {
  serviceName = 'trade-api'
  deployEnv   = 'prod'
}

The library (steps in vars/, helpers in src/) is versioned like any code, and the @1.4.0 pin matters: when the library team ships 1.5.0 with a new deploy step, unpinned pipelines pick it up on their next run. A dozen pipelines failing the same new way at the same time is a library change, not twelve application bugs — check the library's changelog and consider pinning back to the last good version while it is fixed.

Credential binding: the 401 that is not the code

Pipelines authenticate to artifactories, registries and servers through the Jenkins credentials store, injected with withCredentials:

withCredentials([usernamePassword(credentialsId: 'artifactory-svc',
                                   usernameVariable: 'ART_USER',
                                   passwordVariable: 'ART_PASS')]) {
  sh 'curl -u $ART_USER:$ART_PASS https://artifactory.bank.internal/api/...'
}

Failure modes in order of likelihood: the service-account password rotated and nobody updated the store (401s everywhere); the credential ID is misspelled or lives in a folder scope the job cannot see ("no such credential"); the secret is echoed into the console log (Jenkins masks known secrets — if you see a plaintext password in output, the masking failed and the secret must be rotated). Support rule: never paste a credential into a ticket; reference the credential ID and let the owning team rotate it.

Parallel stages: cutting pipeline time

Independent verification steps should run concurrently, not in sequence:

stage('Verify') {
  parallel {
    stage('Unit tests')   { steps { sh 'mvn test' } }
    stage('SAST scan')    { steps { sh './sast.sh' } }
    stage('License check') { steps { sh './licenses.sh' } }
  }
}

Three 10-minute stages become ~12 minutes wall-clock instead of 30. The tradeoff is agent capacity: parallel stages consume one executor each, so a fleet of parallel pipelines can starve the agent pool and queue every other team's builds. When builds sit in "waiting for next available executor" right after someone parallelized everything, that is the cause — add agents or throttle the parallelism, not the pipeline logic.

Agent disconnect recovery

An agent that drops mid-build leaves builds hanging and executors stuck. Recovery order:

  • Check the agent log on the controller (Manage Jenkins → Nodes → agent → Log) — out-of-disk and clock skew are the two classic killers.
  • Relaunch the agent — JNLP agents reconnect on restart; SSH agents need the controller to reach the host and authenticate.
  • Clean stale workspaces — a killed build can leave a locked workspace; the Workspace Cleanup plugin or a manual wipe unblocks the next run.
  • Mark the node temporarily offline while investigating, so new builds do not pile onto a sick agent.

Key takeaway. One flaky agent poisoning many builds looks like "Jenkins is unstable." The node list with per-agent build history tells you it is exactly one machine — evidence beats restarting the controller.
