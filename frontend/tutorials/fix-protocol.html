FIX Protocol Deep Dive

Session management, message anatomy, and a NewOrderSingle dissected tag by tag — from years of onboarding clients and chasing session drops.

What FIX is

The Financial Information eXchange protocol is the messaging standard for electronic trading — orders, executions, market data and allocations all travel as FIX messages over TCP. The common dialects are FIX 4.2 (still everywhere in equities), FIX 4.4 (adds more asset classes), and FIX 5.0 / 5.0 SP2, which splits the session layer out into FIXT so the application version can evolve independently. Every production support analyst in trading eventually learns to read raw FIX the way a mechanic reads an engine.

Session management: the heartbeat of connectivity

Before any order flows, the two sides establish a FIX session — a persistent, sequenced, acknowledged conversation. The session messages (all identified by tag 35):

  • Logon (35=A) — opens the session; carries 98=0 (encryption: none) and 108=30 (heartbeat interval in seconds).
  • Heartbeat (35=0) — sent every HeartBtInt seconds; silence means trouble.
  • TestRequest (35=1) — "are you alive?"; the other side must answer with a Heartbeat echoing 112=test request ID.
  • ResendRequest (35=2) — asks for missed messages by sequence range; the engine of gap recovery.
  • SequenceReset (35=4) — fills gaps administratively (GapFillFlag 123=Y) or resets numbering.
  • Logout (35=5) — orderly close; both sides should expect sequence numbers to continue next session.

Every message carries 34=MsgSeqNum, incrementing per sender. If you receive 34=105 right after 34=103, message 104 is missing — you issue a ResendRequest for 104–104. This gap detection is the entire reliability model of FIX, and most session incidents are sequence-number incidents.

Message anatomy

A FIX message is tag=value pairs separated by a delimiter (shown here as |, really 0x01 SOH). Three tags form the envelope of every message:

TagNameRole
8BeginStringProtocol version, e.g. FIX.4.2 — always first

35MsgTypeWhat kind of message this is (D, 8, 0, A…)
49SenderCompIDWho sent it

NewOrderSingle (35=D), dissected

Here is a buy-side limit order for 500 AAPL at 150.50, walked through tag by tag:

TagValueMeaning
11ORDER123ClOrdID — the client's unique order ID (never reuse within a session)
211HandlInst = automated execution, no broker intervention
402OrdType = 2 → Limit order
44150.50Price — required for limit orders
541Side = 1 → Buy (2 = Sell)
55AAPLSymbol
590TimeInForce = 0 → Day order

The broker answers with an ExecutionReport (35=8): first 39=0 (New), then 39=1 (Partial fill) / 39=2 (Filled) as the order works, each carrying 14=CumQty, 6=AvgPx and 150=ExecType. The order's full state machine lives in tag 39 — support analysts trace "where is my order?" by grepping 11=ORDER123 and reading the 39s.

What production support watches

  • Session drops — heartbeat timeouts at 108-second multiples; first check is always network, second is the counterparty's engine.
  • Sequence gaps — a ResendRequest storm after a failover can flood the engine; throttle and monitor queue depth.
  • Reject storms — a burst of 35=3 (Reject) or 35=j (BusinessReject) usually means a spec mismatch after a counterparty upgrade.
  • Certification — every new client runs scripted FIX certification in UAT: logon, order, cancel, replace, reject cases. Nothing reaches production uncertified.
  • Clock sync — 52=SendingTime drift beyond tolerance gets messages rejected; NTP issues masquerade as application bugs.

Logon (35=A), walked through tag by tag

The Logon message opens every FIX session. Here is a typical one, dissected:

8=FIX.4.4|9=95|35=A|49=CLIENT1|56=VENUE|34=1|52=20261006-14:29:55|98=0|108=30|141=Y|10=042|

TagValueMeaning
35AMsgType = Logon
341First message of the session — sequence starts at 1
980EncryptMethod = 0 → none (TLS is handled below FIX)
10830HeartBtInt — expect a heartbeat at least every 30 seconds
141YResetSeqNumFlag — both sides reset sequence numbers to 1. Omit it and numbering continues from the last session

Some venues also require 553=username / 554=password on the Logon for authentication. The number-one Logon failure in support: one side sends 141=Y and the other does not expect a reset — sequence numbers disagree from message one, and the session never stabilizes. Always confirm the reset convention during certification.

Sequence gap recovery, step by step

When you receive 34=105 immediately after 34=103, message 104 never arrived. The recovery procedure is mechanical:

  • 1. Detect — the engine flags the gap (expected 104, got 105). Do not process 105's business content yet if ordering matters.
  • 2. Request — send 35=2 (ResendRequest) with 7=104 (BeginSeqNo) and 16=104 (EndSeqNo); use 16=0 to mean "everything up to the latest".
  • 3. Receive — the counterparty retransmits the missing messages, each flagged 43=Y (PossDupFlag) — "possible duplicate". Your engine must recognize the flag and not double-book the trade.
  • 4. Fill administratively if needed — if the missing message was an admin heartbeat with no business content, the sender may instead send 35=4 (SequenceReset) with 123=Y (GapFillFlag) and 36=new seq no, closing the gap without retransmission.
  • 5. Resume — once the gap is closed, normal processing continues.

Support watches: ResendRequest storms — after a counterparty failover, hundreds of sessions can request retransmission simultaneously, flooding the engine. Throttle, watch queue depth, and confirm PossDupFlag handling is correct before the storm, not during it.

Common rejects and what tag 58 tells you

When FIX says no, it says it in tag 58 (Text). Learn to read these — they are the fastest diagnosis in connectivity support:

MessageTypical tag 58 textWhat it means
35=3 (Reject)Required tag missing: 44Limit order sent without a price — sender bug
35=3 (Reject)Value is incorrect for tag: 38OrderQty invalid (negative, zero, or bad lot size)
35=3 (Reject)SendingTime accuracy problemClock drift beyond tolerance — check NTP, not the app
35=3 (Reject)MsgSeqNum too lowDuplicate or replayed message; expected higher 34
35=j (BusinessReject)Unknown symbol: XYZReference data gap — symbol not in the security master
35=j (BusinessReject)Order exceeds credit limitPre-trade risk rejection, not a FIX error

A burst of 35=3 right after a counterparty upgrade almost always means a spec mismatch (a tag they now require, or one they stopped accepting). Compare the reject texts against the certified spec before touching your own engine.
