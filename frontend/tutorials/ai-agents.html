Building AI Agents

What an AI agent actually is, how it uses tools and memory, and how to design one that triages production alerts.

Learning path AI Track 1 of 1

Key takeaways

  • The agent loop is perceive → reason → act — tools are the agent's hands on the world.
  • Tools need strict schemas and least privilege: read-only query_logs vs approval-gated restart_service.
  • ReAct interleaves reasoning and acting; memory carries context across loop iterations.
  • Failure modes are concrete: hallucinated arguments ('pricing-engne'), wrong tool choice, unsafe parallel calls.
  • Guardrails are the product: tiered approvals, audit logs, and cost caps (≈ $0.10 per incident at 8 iterations).

The agent loop: perceive → reason → act

A chatbot answers a prompt. An agent works a loop: it perceives (reads the alert, the logs, the dashboard), reasons (decides what the evidence means and what to check next), and acts (queries a tool, runs a command, escalates) — then perceives the result and loops again until the task is done. The loop is what turns a language model into something that can resolve an incident rather than just describe one.

Tools: function calling

An agent can't SSH into a server by thinking about it — it needs tools: declared functions the model can invoke, like query_logs(service, time_range) or get_metric(host, metric). The model outputs a structured tool call, the harness executes it, and the result feeds back into the next reasoning step. Tool design is the real engineering: narrow, well-described tools with safe defaults beat a giant toolbox the model misuses.

tools = [
  { "name": "query_logs",
    "description": "Search application logs. Read-only.",
    "parameters": { "service": "string", "minutes": "integer" } },
  { "name": "restart_service",
    "description": "Restart a service. REQUIRES human approval.",
    "parameters": { "service": "string" } }
]

Note the asymmetry: reading is free, acting needs approval. That single design choice prevents most agent disasters.

Memory and the ReAct pattern

Short-term memory is the conversation and tool results within one incident — what the agent has already checked. Long-term memory persists across incidents: past resolutions, runbooks, known issues. The ReAct pattern structures each loop iteration explicitly as Reasoning (what do I know, what's the next best check) then Acting (call the tool) then Observation (what did the tool return) — written out, so the agent's thinking is auditable later.

Guardrails: what the agent may never do

  • Read-only by default — diagnostics tools need no approval; anything that changes state (restarts, config edits, trade cancellations) requires explicit human confirmation.
  • Scope limits — the agent operates on named services only; it cannot touch databases or production trading engines without an approved runbook.
  • Confidence thresholds — below a confidence level, the agent must escalate to a human instead of guessing; a wrong auto-remediation is worse than a slow one.
  • Full audit log — every reasoning step, tool call and result is logged; in a bank, an agent without an audit trail doesn't get deployed.

Worked example: an alert-triage agent

Design. Input: a PagerDuty-style alert — "pricing-engine CPU > 90% for 5 min." Tools: get_metric, query_logs, list_recent_deploys, check_runbook, page_human.

Decision flow. 1) Perceive: read the alert and pull the CPU chart. 2) Reason: CPU spike started 12 minutes ago — check what changed. 3) Act: list_recent_deploys shows a deploy 14 minutes ago. 4) Reason: correlate — pull error logs since the deploy. 5) Act: logs show a retry storm from the new version. 6) Reason: matches runbook "retry storm" — but restart needs approval. 7) Act: page_human with the full evidence bundle: deploy diff, log excerpts, suggested rollback.

The agent didn't fix it — it did the 15 minutes of triage in 60 seconds and handed a human a decision-ready briefing. That is the realistic, deployable shape of support agents today.

Tool-calling failure modes

Function calling looks robust until the model starts improvising. The failure modes, from most to least common:

  • Hallucinated arguments — the model calls restart_service(service="pricing-engne") with a typo, or invents a host decommissioned in 2023. The harness must validate every argument against the real inventory and reject unknown values.
  • Wrong tool for the job — calling query_logs when the question needed get_metric; usually a sign the tool descriptions are vague. Rewrite the description, don't retrain the model.
  • Dependent calls in parallel — firing call B before call A's result arrives, then reasoning from a missing value. Serialize when outputs feed inputs.
  • Malformed payloads — JSON that almost parses. Strict schemas with required fields, enums for service names, and server-side validation turn these into clean retries instead of incidents.

Worked defense. The agent calls restart_service(service="pricing-engne"). The harness checks the argument against the CMDB service list, rejects it as unknown, and returns: "unknown service 'pricing-engne'; did you mean 'pricing-engine'?" The agent corrects and continues — the typo became a one-line recovery instead of a page to the wrong team.

An evaluation harness for a support agent

Evals are the agent's unit tests: a golden set of 20–30 past incidents, each with the triage a senior engineer actually performed. Score every agent change against the set before it nears production:

  • Diagnostic recall — did it run the checks the senior ran? Missing the deploy-correlation check is a fail.
  • Unsafe-action count — zero unapproved state-changing calls, always. One is a ship-blocker.
  • Time-to-briefing — faster than the human baseline, or the agent isn't earning its keep.
  • Argument hallucination rate — how often tool calls needed harness correction; trending this catches prompt regressions.

Run the harness on every prompt, tool, or model change, and gate deployment on it like a CI pipeline. An agent that passes evals 95% of the time still gets guardrails — evals measure the average case, guardrails cover the tail.

Human-in-the-loop approval patterns

Approvals should be tiered by blast radius, not one-size-fits-all:

  • Auto — read-only diagnostics: logs, metrics, dashboards. No approval, full audit log.
  • One-click approval — state-changing but reversible: service restarts, cache clears. The agent presents the action with its evidence and rollback plan; a human clicks approve.
  • Two-person or ticket-gated — irreversible or money-moving: trade cancellations, database writes, firewall changes. Requires a second approver or a linked change ticket.
  • Break-glass — pre-approved runbooks for known scenarios (restart the wedged feed at 3 AM) with tight scope and automatic expiry.

Worked flow. The agent diagnoses a retry storm and proposes a rollback. It presents: the deploy diff, the error-rate chart, the runbook match, and the rollback command with its 90-second recovery estimate. The on-call engineer clicks approve; the agent executes, verifies the error rate drops, and logs everything. Approvals expire after 10 minutes — the agent never proceeds on a stale yes.

Cost and latency budgeting for agent loops

Every loop iteration is at least one model call, so an uncapped agent is a billing incident waiting for a weekend. Set the budget up front: max 12 iterations, 90 seconds wall-clock, $0.50 per incident — and enforce it in the harness, not in the prompt. Exit early when confidence is high instead of running out the clock.

Worked math. 8 iterations × ~4,000 tokens × $3 per million tokens ≈ $0.10 per incident — trivially cheap. But one runaway loop without an iteration cap once burned $40 over a weekend chasing a flapping alert. The caps are the lesson. Tier the models too: a cheap model for perception and summarization, the strong model only for the reasoning steps — most of an agent's tokens don't need the best brain.

Support angle: meter per-agent spend on the same dashboard as every other infra cost. An agent nobody prices is an agent nobody notices until finance does.

What production support watches

  • Agent actions are changes — every agent with write tools needs the same change-control discipline as a human operator, including rollback plans.
  • Prompt injection — an agent that reads logs and tickets can be misled by malicious content in them; treat tool outputs as data, never as instructions.
  • Cost and latency — each loop iteration is a model call; a looping agent burns budget and delays the page — cap iterations and set timeouts.
  • Evaluation — replay past incidents through the agent and score its triage before it ever touches production; untested agents stay in the lab.

Agent architecture, in one diagram

Every production agent - from alert triage to deployment approval - has the same skeleton:

+--------+     +------------------+     +--------------+
|  User  |---->|   Agent loop     |---->|    Tools     |
+--------+     |  1. perceive      |     |  - db.query  |
               |  2. reason (LLM) |     |  - kb.search |
               |  3. act (tool)   |     |  - ticket    |
               |  4. observe      |     +--------------+
               +--------+---------+
                        |  memory: short-term (this run)
                        |          long-term (past incidents)
                        v
               +--------+---------+
               |   Guardrails     |
               |  allow/deny/audit|
               +------------------+

The loop is the whole game: the model never touches production directly - it only reasons and calls tools. Everything dangerous lives behind the tool layer and the guardrails, which is exactly where support's controls (approvals, audit logs, read-only defaults) plug in.

Tool schema design example

A tool is a contract. This is the schema for the read-only database tool our alert-triage agent uses - note how narrow it is on purpose:

{
  "name": "db_query",
  "description": "Run a READ-ONLY SELECT against the trading
                  replica. No writes, no DDL, 5s timeout.",
  "parameters": {
    "type": "object",
    "properties": {
      "sql":      { "type": "string",
                    "pattern": "^SELECT\\b",
                    "maxLength": 2000 },
      "max_rows": { "type": "integer",
                    "default": 50, "maximum": 200 }
    },
    "required": ["sql"]
  }
}

Design rules that prevent 3am pages: least privilege (SELECT-only, enforced in the tool, not in the prompt), validated inputs (the pattern rejects anything that is not a SELECT), bounded outputs (200 rows max - the model cannot drown in data), and timeouts (a hung query fails fast instead of hanging the loop). If a tool cannot hurt you, the agent using it cannot either.

Practice: easy, medium, hard

Try these before moving on — click a question to reveal the answer.

Easy

1. Name the three steps of the agent loop.

Answer: Perceive (read state), reason (plan), act (call tools) — then loop.

2. Why is query_logs read-only while restart_service needs approval?

Answer: Least privilege: reads can't break production, restarts can — the schema encodes the blast radius.

Medium

3. Alert: 'pricing-engine CPU > 90% for 5 min.' Sketch the agent's first three tool calls.

Answer: get_metric (confirm the reading), query_logs (look for errors), list_recent_deploys (find what changed).

4. The agent calls restart_service with service='pricing-engne' (typo). What defense stops it?

Answer: Schema validation against a registry of known services — unknown names are rejected before execution.

Hard

5. Design approval tiers for a trading-floor support agent.

Answer: Read-only tools auto-run; standard restarts need one click; production deploys need two-person approval; break-glass actions run with a full audit trail.

6. Eight iterations cost ≈ $0.10 per incident. Budget 500 incidents a day.

Answer: $50/day — which is why caps, early-exit rules and iteration budgets are part of the design, not an afterthought.
