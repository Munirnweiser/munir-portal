Frontend / Backend / Middleware

Where a trade actually travels: browser to backend through middleware — and which tier to blame when it breaks.

Learning path FIX & Integration Track 2 of 3

Key takeaways

  • Three tiers, one request: frontend → backend services → middleware (Kafka/MQ) — trace it with correlation IDs.
  • Fills executing but the blotter empty? Consumer lag on the fills topic — the engine is fine, booking is behind.
  • A 429 spike on one API key during volatility is gateway rate limiting — check the quota, not the application.
  • One poison message can block a whole queue — the dead-letter-queue pattern keeps the main flow moving.
  • Support triages per tier: browser console → service logs → queue depth → database.

The three tiers

Frontend is what the trader sees — the order entry screen, blotters, charts. It calls APIs and renders responses; it holds almost no business logic. Backend services do the real work: validation, pricing, booking, risk checks — usually a set of services behind a load balancer, each owning a domain. Middleware is the plumbing between them and to the outside world: message queues (IBM MQ, Kafka), enterprise service buses, FIX engines, file-transfer gateways.

Trader clicks BUY
  → Frontend sends REST order to Order API
    → Order service validates, publishes to Kafka topic "orders"
      → Matching engine consumes, executes, publishes "fills"
        → Booking service consumes fills, writes to database
          → Frontend receives fill via websocket, blotter updates

One click, five hops. An incident at any hop looks identical to the trader ("my order didn't fill") — the job is locating the hop.

Tracing a request across tiers

Modern systems attach a correlation ID to every request, propagated through each hop and logged everywhere. The triage sequence: take the order ID or timestamp from the trader, find the correlation ID in the frontend/API logs, then follow it hop by hop. Where the trail stops is where the failure is. Without correlation IDs you're grepping five log systems by timestamp and hoping the clocks agree — which is why the first question in any bridge call is "do we have the correlation ID?"

Where support looks when each tier fails

  • Frontend broken for everyone — check the CDN/static hosting and the API gateway first; a blank screen for one trader is their browser or VPN, for all traders it's the deploy.
  • Backend slow — check service CPU/memory, database query times, and downstream dependencies; slowness usually lives one layer below where it's felt.
  • Middleware backed up — check queue depth on MQ/Kafka: a growing queue with idle consumers means the consumer is down; a growing queue with busy consumers means the producer is flooding or the consumer is too slow.
  • Messages stuck or duplicated — check for poison messages (one bad message blocking a queue) and whether consumers are idempotent before replaying anything.

Incident walkthrough. Traders report fills not appearing in the blotter, but orders are executing (the exchange confirms). Correlation IDs show fills published to Kafka but the booking service's consumer lag is climbing — it stopped consuming 20 minutes ago. Logs show it can't reach the database: a firewall rule expired. Fix the rule, the consumer drains the backlog, blotters backfill. The frontend was innocent; the database was the root cause; the middleware queue was the symptom that pointed at both.

Rate limiting at the API gateway

The API gateway enforces per-client quotas — say 1,000 requests per minute per API key — and answers excess traffic with 429 Too Many Requests. To the trader it looks identical to the backend being down: orders rejected, screens stale.

Incident walkthrough. During a volatility spike, an algo desk's order burst trips its quota; every order beyond the limit gets a 429. The desk pages support: "the order API is down." Triage: the backend is healthy, but gateway metrics show a 429 spike isolated to one API key. Fix: temporarily raise that key's quota and ask the desk to pace the burst; permanent fix: quota sized for volatility, not for average days. Support lesson: dashboard 429s separately from 500s — they are different incidents with different owners.

Poison messages: the one that blocks the queue

A poison message is one the consumer can never process — a malformed FIX field, a null where the schema demands a value. The consumer crashes or retries forever, and every healthy message behind it waits. The queue depth climbs while the consumer looks "busy," which is exactly backwards from a consumer outage.

The standard pattern: retry a few times (transient errors do clear), then route to a dead-letter queue (DLQ) and move on. The DLQ preserves the evidence; after the bug is fixed, replay it. Two rules from the field: never replay the DLQ blindly — inspect the message first, because replaying a truly poisonous message just re-poisons the queue; and verify the consumer is idempotent before any replay, or the redelivered messages double-book trades.

Worked example. A fill arrives with tag 39 (OrdStatus) set to "9" — not a valid value. The booking consumer throws, retries 3 times, then DLQs it. The blotter shows the order filled at the exchange but unbooked internally. Fix: correct the mapping, replay the single DLQ message, confirm one booking — not two.

Distributed tracing, worked end to end

A correlation ID generated at the edge and propagated in headers (and Kafka message headers, and database comments) turns five systems' logs into one story. Here is a slow order, traced:

corr-id 9f3a-41c2, order 78451231
10:00:01.120  frontend        → POST /orders (corr-id issued)
10:00:01.210  order-api       → validated, published to Kafka (90ms)
10:00:01.260  kafka           → "orders" topic appended (50ms)
10:00:01.900  matching-engine → fill published (640ms ← the slow hop)
10:00:02.050  booking         → written to DB (150ms)
total: 930ms against a 500ms p99 budget

One ID, one timeline, one culprit: the matching engine. Without the correlation ID this would have been five timestamp greps across five systems, hoping the clocks agreed. Support rule: if a system can't propagate the correlation ID, that gap is where the next mystery will hide — file it as tech debt, not trivia.

What production support watches

  • Queue depth dashboards — the single best early-warning signal in a message-driven architecture; alert on growth rate, not just absolute depth.
  • End-to-end latency — per-hop timings expose which tier degrades first; averages hide it, so watch p95/p99.
  • Consumer lag — Kafka consumer lag climbing while the service looks "up" is the classic silent failure.
  • Contract changes — a backend that changes its message format without telling the middleware team breaks every consumer at once; schema registries exist to prevent exactly this.

Latency budget, end to end

An SLA without a per-tier budget is a wish. Slice the total and every tier owns its slice.

Worked example. SLA: p95 under 800ms for order submission.

browser -> CDN ............ 50ms
WAF ..................... 10ms
API gateway (auth) ...... 30ms
backend service ........ 400ms
middleware (MQ) ......... 40ms
downstream adapter ..... 200ms
DB write ............... 70ms
TOTAL .................. 800ms

When p95 hits 950ms, the budget says where to look: gateway at 30ms but backend at 600ms means the problem is downstream of the gateway — check the adapter and the DB, not the edge. Support practice: every tier must emit its own timings (server-timing headers, span durations). Without per-tier numbers, latency triage is guessing with extra steps.

Incident: the poison message

Symptom. 13:00 — the order queue depth climbs: 0 → 40,000 in twenty minutes. Consumers are "running," throughput is zero.

  • Diagnose: consumer logs show the same message ID crashing in a loop — a trade with a null symbol from a bad deploy. The consumer dequeues it, throws, restarts, and re-reads the same message: head-of-line blocking. The dead-letter queue is empty — because no DLQ was ever configured.
  • Root cause: no redelivery cap and no DLQ — one malformed message became a full outage.
  • Fix: move the poison message aside manually, deploy the null-guard fix, and configure a DLQ with max redeliveries (5): after 5 failures the message is quarantined automatically and the queue flows again. Add an alert on DLQ depth — a growing DLQ is tomorrow's incident arriving early.

Lesson. Every queue needs a dead-letter queue and a redelivery cap. Without them, a single bad message is not a data issue — it's a denial of service against yourself.

Interview Q&A: frontend errors, backend logs clean

Q: The frontend shows an error but the backend logs are clean. Where's the bug?

Strong answer: "In the middle — or in what the frontend sent. I open the browser network tab and read the status: 400 means the request was bad — the frontend sent something the API contract rejects, so I diff the payload against the spec. 502/504 means the gateway or proxy — the backend never saw it or timed out. A CORS error means the browser blocked it — the backend may have answered perfectly but without Access-Control-Allow-Origin. Then I correlate with X-Request-ID: frontend → gateway logs → backend logs, following the ID. And if the gateway has no record at all, the request never left the browser — ad-blocker, VPN, or DNS. The interview point: 'backend logs are clean' is data, not a dead end — it narrows the fault to the client, the path, or the gateway."

Practice: easy, medium, hard

Try these before moving on — click a question to reveal the answer.

Easy

1. Name the three tiers.

Answer: Frontend, backend services, and middleware (messaging/ESB such as Kafka or MQ).

2. Orders are executing but fills don't appear in the blotter. First suspect?

Answer: The booking service's consumer lag on the fills Kafka topic.

Medium

3. Walk a BUY click end to end.

Answer: Frontend → REST order API → validation → Kafka 'orders' topic → matching engine → 'fills' topic → booking service → database → blotter.

4. One API key gets 429s during volatility; other keys are fine. Cause?

Answer: Per-key gateway rate limiting — that key exhausted its quota; not an outage.

Hard

5. A poison message halts queue processing. Which pattern, and how does it work?

Answer: Dead-letter queue: after N failed deliveries the message is routed aside with an alert, and the main queue keeps flowing.

6. The correlation ID shows 640ms spent in the matching-engine hop. Next step?

Answer: Profile the engine tier — the slowness is there: GC pauses, lock contention, or a slow downstream call.
